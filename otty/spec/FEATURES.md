## 1. Product surface

**Workspace model.** Three nested levels: a **window** owns the title bar, the tab sidebar (or horizontal tab bar) and all tabs; a **tab** is one independent terminal session and holds a tree of **splits**; a **pane** is the leaf and the only thing you interact with — a terminal, file, folder or URL pane. Unlimited windows, across displays/Spaces; tabs are reorderable, groupable and separable by dividers; panes split in four directions, are drag-rearrangeable across edges/dividers/centers, and can be merged into another tab, torn into a new tab, or torn off into a new window.

**Details panel.** A docked right-side panel that always reflects the focused pane, mirroring the tabs panel on the left; opened with ⌘⇧R, View → Toggle Details Panel, or the title-bar button that appears when you hover the window title. Ships four tabs — Info (cwd, process list, listening ports, open-in actions), Outline (command marks / agent prompts; file TOC, diff list, JSON/YAML/TOML top-level keys, transcript prompts), Git (repo summary, changed files, inline diff), Files (file tree rooted at the pane's cwd). Tabs are reorderable/swappable in Settings, and user-defined **Custom Views** can be added in two kinds — **Terminal Program** (`kind = tui`, a command running in a terminal inside the panel: lazydocker, htop, btm, k9s) and **Web Page** (`kind = web`).

**Command palette** (⌘⇧P, VSCode-style). Every Otty action, including ones with no shortcut, is searchable — palette entries are tagged by scope (pane / window / app). Live "ports" and "line info" entries expand into generated lists; `Split View...` (macOS) and `Fork...` / `Branch...` open pickers with four split directions, New Tab and New Window. `⌘↩` runs and keeps the palette open.

**Open Quickly** (⌘⇧O, Xcode-style). One fuzzy field over nine filters: All (⌘0), Opened (⌘W), Recent (⌘R), Folders (⌘Z, frecency), SSH (⌘S, hosts parsed from `~/.ssh/config`), Agents (⌘G), Current (⌘J), Recipes (⌘E), Files (⌘P). Each result has a default action on ↩ and an Actions popover on ⌘K; typing a full path starting with `/` or `~` that exists pins a Path row at the top. The **Current** filter (⌘J) is scoped to the focused pane and surfaces commands from the shell history (live ones plus commands restored from earlier session logs), URLs/files/folders detected in the terminal output, the outline of a focused file pane, and agent prompts from the focused agent session.

**Outline / Jump To.** An index of every prompt, command and file in a pane's scrollback, built from the OSC 133 marks the shell already emits, exposed as both the Jump To panel (⌘J) and the Outline panel; the same index feeds the `Current` filter of Open Quickly. Requires shell integration.

**Search in Files.** Bundled ripgrep grep of a folder's file contents in a tab of its own, with results/preview two-column layout at ≥ ~700 pt, toggles for case-sensitive, whole-word, Rust-regex, include and exclude globs; results stop at 5000 matches and render the first 800 rows.

**Status bar.** **Planned, not implemented yet** — the page contains nothing else.

**Find.** In-pane search across visible buffer and scrollback of the focused pane (⌘F; ↩/⌘G next, ⇧↩/⇧⌘G previous, Esc close), with live highlight and an `N of M` counter, plus case-sensitivity and regex toggles (`Aa` = case sensitive, `.*` = Rust regex; default is case-insensitive literal). Scope is the focused pane only — **terminal pane**: visible viewport + full scrollback; **file pane**: full file; **folder pane**: file names only, not contents. ⇧⌘F is Global Search across every open tab's scrollback, shown in a dedicated tab.

**Drag & drop.** Files, folders, URLs and text snippets from Finder/browsers/any standard-pasteboard app land on the focused pane's four edge targets, each edge split into a green (inner/terminal) half — open a new terminal rooted at the dragged path — and a blue (outer/otty) half — open as a folder/file/URL pane. Otty's own tabs and panes are draggable too (reorder, move between windows, tear off; pane drop zones are split/insert/swap/merge-new-tab/new-window).

**Files and links.** What gets detected in live output and scrollback: absolute paths (`/usr/local/bin/foo`, `/Users/me/project`), tilde paths (`~/project/file.swift`), relative paths (`./src/lib.rs`, `../config/foo.toml`), paths with line / column suffixes (`src/lib.rs:42`, `src/lib.rs:42:5`), `http://` / `https://` / `file://` URLs, and OSC 8 hyperlinks emitted by programs. Relative paths resolve against the pane's cwd from OSC 7, and holding ⌘ underlines what is clickable while ⌘-hover shows the full path in the bottom-left (macOS Lookup / Quick Look previews the file or URL). ⌘-click opens in the best handler (file pane for text, default app otherwise), ⌘⇧-click reveals in Finder / copies the URL, right-click gives a context menu (Open Link / Open File / Open Folder, Open with, Copy Path / Copy URL, Reveal in Finder, Change Directory Here, Open in Otty). Beyond that the product ships a **file pane/editor** (syntect highlighting, ~120 bundled grammars, Markdown/reST/SVG/HTML live preview, Mermaid diagrams, image zoom, Quick Look for PDF/video/office/fonts, hex view for binaries, agent-transcript rendering; ⌘S saves in Edit mode, ⌘R reloads from disk discarding unsaved changes, outside edits raise a "Reload / Keep my changes" banner, and file panes are designed for text up to a few MB — larger files fall back to a streamed view with no in-place edit), a **folder pane**, and a built-in **WKWebView browser pane** with a non-persistent data store.

## 2. Workspace model

**Nesting.** `window → tab → pane (terminal | file | folder | URL)`; a tab may contain a split tree. Pane type is determined by what opened it; a rule on a file/folder pane can match the file name (`*.md`) but "Never matches a terminal pane, which has no file."

**Split semantics.** ⌘D split right, ⌘⌥D split left, ⌘⇧D split down, ⌘⌥⇧D split up; ⌘W closes the focused pane. Dragging a pane onto **any edge** of a target pane maps the four edges to split above/below/left/right and is then "resolved against the whole tab", so one drag can turn a 2×2 grid into a full-height side column (explicitly more capable than Ghostty's neighbor-swap). Divider drag resizes; double-clicking a divider or the border of split views equalizes panes; ⌘⌃⇧+arrow nudges a divider from the keyboard; ⌘⌃= runs Equalize Splits. ⌘⇧↩ zooms/unzooms a split. Unfocused panes are drawn faded per `unfocused-split-opacity` (default `0.6`), which is a separate knob from `faint-opacity`.
When a tab has only one pane, pane-cycle shortcuts pass through so they stay free for other uses.

**Focus / switching.** ⌘] / ⌘[ next/previous pane; ⌘⌃+arrows focus by direction; ⌘⇧] / ⌘⇧[ next/previous tab; ⌘1–⌘9 jump to tab index; ⌘⇧U jumps to the next tab carrying an unread badge (wrapping). ⌘⇧O searches across every tab/pane. The focused pane carries a highlight in its toolbar and owns pane-scoped shortcuts (⌘F, scrolling, paste).

**Tab ordering and grouping** (vertical sidebar only — "the horizontal bar keeps a flat strip"). Filter button at the top of the tabs panel or right-click an empty area opens:
- **Group**: No Grouping (default) / By Project (git repo or project root) / By Date (Today, Yesterday, …; "when the tab was last active").
- **Order**: Created Time (default, oldest-opened first) / Updated Time (most-recently-active first) / Manual (set implicitly the moment you drag a tab to reorder; the menu deselects the time orders).
- **Divider**: Insert Divider (also right-click between two tabs) creates a named separator; a divider can be renamed, dragged and deleted like a tab; Remove All Dividers clears all. Dividers are disabled while a Group mode is active.
Group, order and collapsed sections are remembered per window across session recovery.

**New tab position** — `new-tab-position` (default `auto`): `auto` = context-aware (empty tabs from ⌘T land at the end of the current section — just before the next divider or the end of the strip; tabs opened with content drop in right after the current tab); `end`; `after-current`.

**Tab panel/bar auto-hide** — `auto-hide-tabs-panel` (sidebar-left) and `auto-hide-tab-bar` (tabs-top/tabs-bottom), both default `default`: `default` = no automatic hiding, and a new window opens with the same state as the window it came from; `always` = shown by default, new windows always open with it visible, still hideable per window with the toggle; `auto` = driven by tab count — hidden with a single tab, shown at two or more, updating as tabs open and close. The show/hide toggle is per window, and each window restores its own panel state across a restart.

**Titles.** Window title (title bar) and tab name (sidebar/bar) are tracked separately. OSC 1 sets the icon name and drives the **tab name**; OSC 2 sets the **window title**; OSC 0 sets both. If a program sets only OSC 2, the tab name falls back to the window title. Switching tabs updates the window title to the newly active tab. Rename via right-click → Rename Tab... (also Command Palette and the Shell menu) with two modes: **Name** — a fixed title that fully replaces the dynamic one, with OSC updates from the program ignored while a name is pinned — and **Prefix** — text prepended to the dynamic title, so it keeps updating while staying identifiable (a `prod: ` prefix in front of the live program name reads `prod: ssh db-01`). Empty Name or the reset button returns to the automatic title. A renamed or prefixed tab keeps its customization across session recovery. Hand renames beat rules ("the rules provide the default label, not a lock"). `title-from-osc` (default `true`) — the UI toggle "Programs Can Set the Title" — turns program renaming off.

**Tab rules** (Settings → View → Tabs & Title; three independently-configured rows — **Project Alias** (a short name, e.g. `Otty` instead of `~/Workplace/otty`), **Icon** (one from the built-in set or any emoji, plus a colour taken from the terminal's own palette so it follows the theme) and **Title** (a template) — each showing its current rule count). Every rule starts with a `When` condition — working-directory path, foreground command, coding agent, SSH host, or file-name pattern like `*.md` for file/folder panes. A path with no `*` also covers everything beneath it. **Order is priority: the topmost rule that matches wins**, and alias/icon/title are decided separately, so a broad `~/Workplace/*` rule can give a common icon while a higher rule overrides only the title. Editors offer **By item** (one row per thing a rule can set; where priority is ordered) and **By project** (one row per condition) views.

**Tab icon vs badge** — `tab-icon-placement` (default `combined`): `combined` = one indicator on the right, showing your icon, which a status badge takes over while a command is running, has failed, or is waiting for input; `separate` = the icon moves to the left of the tab label and badges keep the right, the shell name (`zsh`, `fish`) is hidden, a file or folder pane's own icon becomes the tab icon when no rule supplied one, and the window title carries the icon as well.

**Tab badges.** Automatic status indicators: Spinner (session busy — long-running command or `OSC 9;4;1` progress), Checkmark (a command just finished; shown briefly then clears), Accent dot (command exited successfully (0) in a tab you're not looking at), Error triangle (non-zero exit), Hand (an agent is waiting for input), Coffee cup (`caffeinate` keeping the system awake for this tab), Shield (`sudo`/`su` session active), Devices (session running on a remote host via SSH). Per-badge display is configurable from Settings → Shell → Tab Badge, the menu bar, the context menu and the titlebar dropdown. `otty watch <cmd>` produces Spinner/Checkmark/Error triangle plus a notification. Right-click → Clear Badge dismisses by hand. The **active** tab never shows the success dot or completion checkmark; spinner, awaiting-input, caffeinate and sudo always show.

**Move / close / reopen.** Drag a tab in the strip to reorder, move to another window, or tear off; while dragging, the tab follows the cursor as a floating preview and the original dims to a ghost. Menu equivalents: Move Tab to New Window, Move Up, Move Down. ⌘W cascades — it closes the focused pane first, then the tab when that was its last pane, then the window when that was its last tab. ⇧⌘T reopens the last closed tab from a stack (walking back most-recent-first, each restored with its working directory and title); the list persists across restarts and crashes.
Shortcuts: Pane split ⌘D / ⌘⌥D / ⌘⇧D / ⌘⌥⇧D, close ⌘W; Tab open ⌘T, close ⌘W; Window open ⌘N, close ⇧⌘W, minimize ⌘M, toggle full screen ⌘⌃F. All customizable under Settings → Keybindings.

**Window options.** `window-size` (default `remember`): `remember` reopens at the last-closed size/position; `grid` sizes the grid to `window-cols` × `window-rows` (default `80 × 24`) at the active font's metrics with chrome added on top; `frame` uses a literal pixel content rect `window-width-px` × `window-height-px` (default `1000 × 600`). Drag any edge/corner to resize; the grid reflows. **Pin Window** (View menu, or Pin Window / Unpin Window from the palette) floats the window above all apps and shows a pin button in the title bar. **Picture in Picture** (View menu, `pip`) pops a pane into a system floating window with two modes: Current Pane (keeps showing the chosen pane regardless of focus) and Follow Active Pane (mirrors whichever pane is active); closed by Close Picture in Picture or the standard PiP controls.
When all windows are closed: **Quit When All Windows Closed** and **New Window When All Windows Closed** are mutually exclusive; if the first is on, the second is disabled. Close confirmation is two independent keys under Settings → General: **Running Process** (`process` — prompt only when a child process other than the shell is still running, e.g. an editor, a server, an ssh session), **Always** (`always`), **Multiple Tabs** (`multiple_tabs`, window only) and **Never** (`never`), surfaced as `confirm-close-tab` / `confirm-close-window` / `confirm-close-pane`. **Hide Close Button Dot** (`window-hide-dirty-indicator`, macOS) suppresses the traffic-light dot.

**Open options / starting directory.** Per scope: Settings → Shell → Working Directory — Same as Current Tab (`inherit`) reuses the focused pane's cwd; Home (`home`) starts at `$HOME`; the global `working-directory` key sets a fallback for all of them and also accepts an absolute path. Newly-opened non-terminal views arrive by dropping onto a pane edge, or `otty view <file>` / `otty open <dir-or-url>`.

**Save/restore layouts.** ⌘S (File → Save…) saves the current layout as a **Recipe** with a scope (Current Tab / Current Window / Commands) and a content level (Layout Only / Include Scrollback / Include Commands (replay on open)). Restore from File → Open Recipe…. Full detail in §5.

**Session recovery (workspace aspect).** Tabs come back with their working directory and title; group/order/collapsed-section state and each window's panel state are restored per window. Mechanism and options: §5.

## 3. Terminal features

### Autocomplete / Inline Suggest

Ghost-text and candidate-panel completion driven by a Fig-compatible spec database (715 commands at last count — git, npm, kubectl, docker, aws, …) plus on-device learning. No summoning key: a moment after you stop typing, the most likely continuation appears as dim ghost text; when several completions are plausible the candidate panel can open beneath the cursor instead. Ghost text is drawn only when one suggestion clearly leads — the only match, or a command you run in this folder noticeably more often and most recently — so "a ghost is never a coin flip"; when two remembered variants disagree Otty previews only the next word they share. Accept with Tab (or → when `autocomplete-shortcut = tab+right-arrow`; with `right-arrow` only → accepts and Tab always goes to the shell's own completion). Typing shortens the ghost a character at a time; **Backspace lengthens it again**, the deleted character turning dim; Esc dismisses it without leaving the line (with several candidates waiting, the first Esc clears the ghost and the second opens the panel).

Candidate panel: dropdown beneath the cursor, ↑/↓ to move, Return or Tab to accept, Esc to dismiss, click a row; **up to eight rows visible**, plus a side column with the selected item's description. Each row carries a kind icon: subcommand, option/flag, argument, file, folder, alias, snippet, learned command, README command, or a "did you mean…" fix.

Configuration keys (all eight):
| Key | Default | Values / effect |
|---|---|---|
| `autocomplete-shortcut` | `tab` | `tab`, `tab+right-arrow`, `right-arrow` (only → accepts), `ctrl+space`, `disable` |
| `autocomplete-show-candidates` | `escape` | `disable`, `auto` (whenever there are ≥ 2 matches), `escape`, `option-escape` (Option+Esc / F5) |
| `autocomplete-inline-suggestion` | `true` | draw the faded ghost text |
| `autocomplete-inline-provider` | `otty` | **Windows, PowerShell only**: `otty` (PSReadLine's own prediction is switched off) or `psreadline` (PSReadLine's prediction first, Otty's when it has none) |
| `autocomplete-on-device-learning` | `true` | master privacy gate for history, `--help` probes, README scan |
| `autocomplete-skip-secrets` | `false` | never record a command that looks like it carries a password, token or API key; **new commands only** |
| `autocomplete-history-ignore` | (none) | glob patterns for commands never recorded, e.g. `ssh *`, `export *TOKEN*` |
| `autocomplete-description-language` | `system` | `system`, `english`, `chinese` |

Sources and behaviours: spec data ships as a single in-app database, refreshed only by **Update Now** on the Completion Database row in Settings → Controls → Autocomplete — no automatic background download, and locally-taught entries are never overwritten. **Recent Used** is ranked by frecency "with a strong boost for the current session"; commands matching `autocomplete-history-ignore` are skipped entirely, and a command that exits **127** (not found) or an obviously mistyped `--flag` is pruned back out of history. For a tool with no spec, Otty offers file/folder names once you have typed the first character of an argument (never a whole folder listing on an empty argument), adapts to whether you pass words or paths (`mytool deploy` twice ⇒ stops offering paths; one `mytool ./build` ⇒ they return), and always completes a word that looks like a path (starts `./`, `../` or `~/`). **Whole command lines you've run here** are remembered per folder and sit above every other suggestion; accepting them replaces the **entire line**, not just the word under the cursor; they are strictly folder-scoped; a command interrupted with Ctrl+C is still remembered, one that turns out not to exist is dropped. **Auto correction** reads a failed command's error and offers the fix as ghost text on the next line, recognizing the correction output of git, npm, cargo, pip, brew, rustup and the shell's command-not-found handler. **Package-runner recovery** recognizes npx, npm exec, pnpm dlx, yarn dlx, bunx (Node); uvx, pipx run, poetry run, pdm run, hatch run, rye run (Python); bundle exec, gem exec (Ruby); composer exec (PHP); half a runner is enough if unambiguous (`pn` finds `pnpm dlx`, a bare `p` waits for one more letter). `otty learn '<cmd>'` pins a command to the current folder and is offered first there (repeat bumps its rank); Otty does **not** auto-scan package.json, Makefile or justfile, but does read fenced code blocks from a project's README. `otty learn <binary>` runs `<binary> --help` (falling back to `-h` or a help subcommand), parses options/subcommands and writes a spec into the local database, tagged separately and surviving app updates.
Privacy: fully offline; a value after a flag like `--password`, `--token` or `--api-key` is dropped before anything is written, but whole command lines are kept verbatim ("a secret typed directly on the command line is stored with it unless Skip Secrets is on") and the database is on disk like `~/.zsh_history`. Five things keep a line out of sight, or out of the database entirely: **Skip Secrets** on — commands that look like they carry a credential are then never written to history at all (`--password=…`, `API_KEY=…`, an issuer-stamped value like `sk-…` or `ghp_…`, credentials inside a URL, an `Authorization: Bearer` header, and `mysql -uroot -phunter2` where the password is glued to the flag), applying to commands you run from then on, with `otty learn '<cmd>'` as the deliberate way to keep one anyway; **a leading space** — a command starting with a space is never recorded at all (the shell's own "don't remember this" gesture); **History Ignore Patterns** (Settings → Advanced, globs like `*--token*`) — skipped before anything is written; **Shift+Delete on a remembered line in the candidate panel** — forgets that one line; **Clear my data** — a bulk wipe that lists *Full command lines* separately from *Command history*, so you can drop stored commands without losing the argument frequencies everything else ranks by. `--help` probes run inside a network-denied sandbox. The **only** network access is pressing Update Now, which downloads and uploads nothing in return. Settings → Controls → Autocomplete switches, each independently: **Inline Suggestion** off hides the ghost text; **Candidate Panel** set to *Disabled* stops the Esc / Option+Esc dropdown opening; **Accept Suggestion** set to *Disabled* frees the accept key entirely; **Hide Secrets** on stops credential-looking commands *appearing* in suggestions (they are still recorded, so turning it back off brings them back); **On-device Learning** off keeps the bundled specs but records nothing new — no argument frequencies, no whole command lines, no `--help` probes, no README reads. Switching off both Inline Suggestion and Candidate Panel disables the feature entirely and the spec database is never consulted.
`[conflict]` The Shell Integration page states that on-device autocomplete learning learns "only commands that exit 0", while this page states that a command interrupted with Ctrl+C is still remembered (a nonzero exit) and that only a command that turns out not to exist is dropped.

### BiDi / RTL Text

Renders Hebrew, Arabic and mixed RTL text in reading order while the **terminal grid stores text in logical order**, so copy, paste, find, shell editing and program output are unaffected; the renderer reorders each display line only when it draws the screen. Requires Otty 1.2.0 or later. Key `bidi` (default `true`) — "Bidirectional (RTL) text". Cursor movement stays visually aligned: Left/Right follow the visual shape of RTL text while the underlying text keeps the order the shell expects; caret and selection track what is on screen. Apps that lay out RTL themselves can be handled per session by turning the setting off. **BiDi-aware applications can opt out for their own session with the standard ECMA-48 Bidirectional Support Mode (BDSM, mode 8)**; while an app is in explicit BiDi mode Otty suppresses its implicit per-line reordering until the app returns to implicit mode. Copy/paste always yields logical-order text, by design. Per display line the algorithm gives: Hebrew and Arabic runs shown right-to-left; numbers, punctuation, paths, prompts and Latin words keeping their expected placement inside the line; pure left-to-right output left untouched; and selection, copy, paste and search all using the original logical text rather than the visual drawing order.

### Box Drawing

Pixel-perfect rendering of Unicode box-drawing, block, Braille and Powerline glyphs, drawn analytically rather than rasterized from a font. Arrows (← → ↑ ↓) and solid triangles (◀ ▶ ▲ ▼) are treated as part of box-drawing: when one sits next to a connecting rule (│ ─ ┃ ═ ┼ …) its stem extends to meet the rule instead of leaving a gap — arrows get a box-aligned stem + chevron, triangles a flat back flush on the rule's edge; standalone glyphs in prose/TUIs are unaffected. Config key `arrow-box-drawing-join` (default `true`); UI: Settings → All Settings, search "Join arrows & triangles to box-drawing rules" (turn off for the standard behaviour).

### Copy and Paste

**Copy:** select text, then ⌘C, Edit ▸ Copy or the right-click menu. `copy-on-select` (default `false`) drops every selection straight into the clipboard; `clipboard-trim-trailing-spaces` (default `false`) strips trailing spaces from each copied line; `selection-clear-on-copy` drops the highlight after an explicit copy. Cut is ⌘X (copy + delete when the selection is editable prompt text; a plain copy on read-only text). GUI-only configuration — no config file needed beyond those keys.
**Paste:** ⌘V, Edit ▸ Paste or the right-click menu; bracketed paste is handled automatically so supporting programs receive the text as one inert block instead of interpreting newlines as Enter. Pasting files copied in Finder inserts their paths, shell-escaped and space-separated (the same text as dragging them onto the pane), for any file including images — the original path, not a copy. **Text always wins over a picture**; an image with no text and no path behind it (screenshot) is saved to a temporary file and that path is pasted.
**Paste protection** (`clipboard-paste-protection`, default `true`) warns before pasting content that could run something unintended, showing a preview; you can always choose Paste Anyway or Cancel. The check is skipped inside full-screen TUIs (vim, less) and, when `clipboard-paste-bracketed-safe` (default `true`) is on, for programs that advertise bracketed-paste support. The dialog flags: **multi-line text** (earlier lines would execute the moment they're pasted), **a trailing newline** (the command would run on paste, before you can review it), **sudo / su** (the paste may run with elevated privileges) and **control characters** (possible terminal-escape injection hidden in the text).
**Paste as…**: Paste Selection (X11 middle-click convention); Paste File Base64-Encoded…; Paste Escaping Special Characters (shell-escapes the text); Bracketed Paste (forces bracketed-paste markers even if the program didn't ask); Paste and continue in Composer.
**Program clipboard access — OSC 52.** `clipboard-write` (default `allow`) and `clipboard-read` (default `ask`), each `allow` / `ask` (prompt every time) / `deny`; read defaults to Ask "because letting a remote program silently read your clipboard is the riskier direction". Also gated by `privilege-clipboard-shell` (default `true`).

### Cursor and Mouse

**Cursor style** — `cursor-style` (default `block`; values `block`, `bar`, `underline`, `block_hollow`, also `block-hollow`); `cursor-style-blink` (default `default_off`; `default_off`, `default_on`, `always_off`, `always_on` — `default_*` set the initial blink but let a program override it, `always_*` pin it and ignore programs; legacy `true`/`false` parse as `always_on`/`always_off`); `cursor-animation` (default `off`; `off`, `smooth` — Smooth glides the caret on same-row moves and adds a small overshoot on click/focus). Colors: `cursor-color` and `cursor-text` (default `(theme)`; in the UI, Theme → Cursor element and "Text color under cursor", leaving either at Default follows foreground/background); `cursor-opacity` (default `1.0`, range `0.0`–`1.0`).
Programs can override the cursor at runtime — shape via **DECSCUSR (`CSI <n> SP q`)** and blinking via DECSCUSR's blinking variants or **DEC private mode 12 (`CSI ? 12 h/l`)**. Polarity: the shape override always follows the running program; only blinking has the Always/Default policy.
**Mouse** — `focus-follows-mouse` (default `false`) focuses the pane under the pointer without clicking; `right-click-action` (default `context-menu`; `context-menu`, `copy`, `paste`, `copy-or-paste`, `ignore`) — ⌃+right-click always opens the menu; `mouse-hide-while-typing` (default `false`); `cursor-click-to-move` (default `true`) clicks in the prompt to move the shell cursor there by sending the right number of arrow keys, even across soft-wrapped rows.
**Mouse reporting** — `mouse-reporting` (default `true`, UI "Allow Mouse Capture") plus `privilege-mouse-shell` (default `true`). Modes are cumulative via DECSET: **Normal (?1000)** button tracking — press and release of left/middle/right plus the wheel; **Button-event (?1002)** adds motion while a button is held, one report per cell crossed; **Any-event (?1003)** adds bare motion. Every report carries live modifier state (⇧ Shift, ⌥ Option/Meta, ⌃ Control); coordinates are encoded in **SGR form (?1006, `CSI < b ; col ; row M/m`)** so columns and rows beyond 223 report correctly; drag/motion are de-duplicated at cell boundaries, matching xterm / Ghostty.
**Bypass** — `mouse-shift-to-select` (default `true`, UI "Bypass Mouse Reporting"; options None / Shift / Ctrl / Alt / Ctrl+Shift / Super; default ⇧ Shift, `None` turns the bypass off) hands one gesture back to Otty for native selection or link opening. On macOS ⌘-click already bypasses mouse reporting.
**Mouse cursor shape (OSC 22)** — full-screen TUIs (yazi, btop, mc, ranger) choose the pointer over the pane; Otty maps the standard CSS cursor names to the closest native pointer and programs reset with `\e]22;default\e\\` (or by exiting). `mouse-scroll-multiplier` (default `3.0`, compound form `discrete:3.0,precision:1.0`) scales Otty's own scrollback scrolling only — not wheel events forwarded to a program that reads the mouse itself.

### Hint Mode

Labels every matching target in the visible viewport with a one-, two- or three-letter code; type the complete code to run the configured action. **No default shortcut**; on macOS start the original open-link action from Shell → Open Link (Hint Mode), the Command Palette, or bind one of `Hint: Open` / `Hint: Copy` / `Hint: Paste` / `Hint: Reveal` (Paste and Reveal have no default binding). With Hint: Open or the legacy `toggle_hint_mode`, **hold Shift while typing the final label character to copy instead of open**. Esc cancels; Backspace removes the last label character.
Action format `texthint:<matcher>:<action>` (custom bindings), with the built-in matchers: `link` (URLs, OSC 8 hyperlinks, and file paths), `url`, `path`, `word` (word-like tokens of at least three characters), `ip` (IPv4 and IPv6), `hash` (7–64 character hexadecimal hashes). Actions are `open`, `copy`, `paste`, `reveal`; `paste` inserts the exact displayed text and uses normal paste-protection checks; `copy` uses the resolved URL/absolute path for link targets and the exact displayed text for text matchers. Custom named patterns come from repeated `hint-pattern` lines and are then used as the matcher: if the expression contains a numbered capture group Otty hints the first group, otherwise the whole match; names may contain ASCII letters, digits, `_` and `-`, and `link`, `url`, `path`, `word`, `ip`, `hash` are reserved; invalid names/expressions are rejected at config load. An `open` action may include a URL template where `{0}` is replaced by the exact matched text; a `run` action launches a command without invoking a shell, the template is split into arguments **before** `{0}` is substituted (so matched terminal text cannot inject extra arguments or shell operators), and if the template omits `{0}` the matched text is appended as the final argument.
Scope: hints are computed from the visible viewport when the mode starts; labels stay attached to their targets while you scroll but newly visible text is not added until you start Hint Mode again. One documented inconsistency: the action-format section states `texthint:<matcher>:<action>` while the examples use `hint:word:paste`, `hint:ticket:copy`, `hint:pr:paste`, `hint:ticket:open:<url>` and `hint:ticket:run:<cmd>` — the `hint:` prefix is the one used in every working example. `[conflict]`

### Input

**Native-GUI input.** Click any pane to hand it the keyboard; in a split the clicked pane lights up and starts receiving input (or use `focus-follows-mouse`). The standard Mac editing/navigation chords are mapped onto the terminal and send the readline sequence the shell expects, so they behave the same in every shell; each is an ordinary keybinding under Settings → Key Bindings ▸ Text Editing: ⌘A select all; ⌘C/⌘X/⌘V copy/cut/paste; ⌘Z / ⌘⇧Z (⌘Y) undo/redo; ⌘F / ⌘G / ⌘⇧G find / next / previous; ⌘← / ⌘→ line start/end; ⌥← / ⌥→ word left/right; ⌘⌫ / ⌘⌦ delete to line start/end; ⌥⌫ / ⌥⌦ delete word left/right; ⌘↑ / ⌘↓ page up/down; ⇧+arrows extend a selection. The word chords work whether or not Option as Alt is on. **Undo/redo** applies to the current prompt line only — rapid typing coalesces into a single undo step, and undo is unavailable inside full-screen programs (vim, less, an editor).
**IME**: full input-method support (Chinese, Japanese, Korean, dead keys); composing text is shown inline at the prompt, the candidate window tracks the cursor, and committed text is sent on confirmation.
**Kitty keyboard protocol** (`kitty-keyboard`, default `true`, Settings → Advanced): modern unambiguous key encodings (**CSI u**) that let programs distinguish Tab vs ⌃I, Esc vs ⌃[, modified keys and key-release events (Helix, fish 4); programs opt in at launch and anything that doesn't request it falls back to the classic encoding automatically.
**modifyOtherKeys** (xterm XTMODKEYS) is also spoken for programs that reach for it instead — notably Emacs and fish 4 — delivering ⌃;, ⌃., ⌃/ and ⌃Space as distinct keys; it is fully automatic, snaps back to classic encodings when the program exits **or crashes without cleaning up**, and has nothing to configure.
**Keyboard options** — `macos-option-as-alt` (default `false`; `true`, `false`, `left`, `right` — treat Option as Alt/Meta for both keys or just one); `shift-arrow-select` (default `true` — ⇧+arrows drive a native selection instead of sending arrow escapes; turn off to pass them to a TUI); **Allow VT100 Application Keypad Mode** (`vt-keypad-app-allowed`, default `true`) honors a program's **DECKPAM** request so vim/emacs/less keypad bindings work — off makes keypad keys always type literal digits.
**Secure Keyboard Entry** — a macOS-level protection that stops other apps (keyloggers, screen-capture helpers, scripting tools) from observing keystrokes while Otty has focus; a title-bar pill shows the state, hideable with `secure-input-indication`. `auto-secure-input` (default `true`) turns it on automatically when the active session appears to be asking for a hidden password, such as sudo, ssh or login, and releases it when the prompt finishes; Edit → Secure Keyboard Entry toggles it manually.
**Composer** — a multi-line editor sliding up from the bottom of the focused pane: ⌘⇧E toggles it (also Edit ▸ Composer, the Command Palette, the terminal right-click menu); ⌘↩ sends (paste draft into the terminal and close); ⇧↩ inserts a newline; Esc cancels, keeping the draft. It matches the terminal theme and can be popped out into a floating window that stays on top.
**Prompt Queue** — ⌘⇧M opens the queue input bar at the bottom of the focused pane (Edit ▸ Prompt Queue…, or the Command Palette); type a line and press ↵ to add it, the ↳ arrow on a row to send it right now, the trash button to drop it. Otty dispatches the next item only when the shell is back at an idle, empty prompt; full-screen TUIs pause the queue; for agent panes it waits for the agent to go idle between turns. The Composer can hand its lines straight to the queue.
**Native macOS features** — selected text is offered to any Service that accepts text; Edit ▸ Insert from gathers File Path…, Screenshot, and Import from iPhone or iPad (Continuity Camera), which saves the photo/scan/sketch to a temp file and drops the shell-escaped path into the prompt.

### Privilege and Notifications

**Desktop notifications.** Any of three OSCs pops a native macOS notification:
```bash
printf '\e]9;Build finished\a'                       # OSC 9 — body only
printf '\e]777;notify;Deploy;Production is live\a'   # OSC 777 — title + body
printf '\e]99;;Build finished\e\\'                   # OSC 99 — simplest (single chunk)
```
OSC 9 mirrors the iTerm2 convention (body string); OSC 777 (urxvt-style) adds a title; OSC 99 is the kitty notification protocol — richer structured payload (urgency, base64 encoding, chunked transmission, replace-by-id, capability query). Programs typically emit OSC 99 first and fall back to OSC 9/777. Gated by `privilege-notification-shell` (default `true`, UI "Notification — Shell Controlled"); off ignores notification OSCs.
**Bell.** BEL (0x07) plays the system alert sound (`NSSound.beep()`), gated by `privilege-sound-shell` (default `true`, UI "Sound — Shell Controlled"). **There is no visual (flash) bell — the bell is audio-only.** `privilege-sound-on-error` (default `false`, UI "Sound on Error Exit") beeps when a command exits non-zero (requires shell integration).
**Bounce Dock Icon** (default on, macOS): when a notification fires while Otty isn't the active app, Otty requests user attention (`NSApplication.requestUserAttention`) — driven from the notification OSCs (9/777/99) rather than from BEL. macOS suppresses banners while Otty is foreground; `notification-foreground` (default `off`; `off`, `always`, `tab-unfocused` — "tab-unfocused shows one only when the notification comes from a tab that isn't the active one") overrides that. **System permission**: banners are ultimately gated by the macOS per-app permission in System Settings → Notifications → Otty; the System Permission row at the top of Settings → Shell → Notification shows current status (green dot allowed, amber/red when banners won't appear) with an Open System Settings button, refreshing when you switch back to Otty.
**Notification options** (per-pane defaults; shell-integration-driven ones need shell integration on; the same toggles appear in the Privileges menu and the command palette):
| Toggle | Key | Default | Fires when |
|---|---|---|---|
| Notify on Finish | `privilege-notification-on-finish` | off (`false`) | any command finishes (exit 0) |
| Notify on Error | `privilege-notification-on-error` | on (`true`) | a command exits non-zero |
| Notify on Watch Finish | `privilege-notification-on-watch-finish` | on (`true`) | an `otty watch`-wrapped command finishes |
| Notification — Shell Controlled | `privilege-notification-shell` | on (`true`) | allow shell apps to post notifications (OSC 9 / 777 / 99) |
| Notify While Foreground | `notification-foreground` | off | banner policy while Otty is frontmost (off / always / tab-unfocused) |
| Bounce Dock Icon | — | on | bounce the Dock when a notification arrives and Otty isn't active |
| Sound on Error Exit | `privilege-sound-on-error` | off (`false`) | beep on a non-zero exit |
| Sound — Shell Controlled | `privilege-sound-shell` | on (`true`) | allow shell apps to ring the bell (BEL) |
**Notification Sound** is a multi-select opting specific categories into the default alert sound; empty (the default) keeps every banner silent; the categories are independent of the Notify-on-… toggles (those decide whether a banner appears, this decides whether it makes a sound) and separate from the bell and Sound on Error Exit, which beep directly. The three categories are **On Error Exit** (a command exits non-zero), **On Command Finish** (a command — or an `otty watch`-wrapped command — finishes) and **App Notifications** (a shell app posts a notification, OSC 9 / 777 / 99).
**Code-agent notifications** — Claude Code, Codex and OpenCode report task state over IPC, so their notifications fire **without shell integration**. Two toggles under Settings → Shell: **Code Agent — Notify When Task Completes** (on by default — notification when the agent finishes a task and goes idle) and **Code Agent — Notify When Awaiting Input** (on by default — when the agent is waiting on your approval or input). Matching badges and `otty watch:claude` are in Progress State.
**Privilege settings** gate risky escape sequences and their defaults are "conservative". **Title** (Settings → Advanced): `Title Report` (off by default — let apps read the window title back via **OSC 21 / XTWINOPS**; a program that can both set and read the title can smuggle data out of a pane) and `Title — Shell Controlled` (on by default — let apps change the tab / window title, OSC 0 / 2). **Clipboard** (Settings → Advanced): `Clipboard — Shell Controlled` (on by default — master switch for OSC 52), `Clipboard Read` (ask by default), `Clipboard Write` (allow by default). **Secure keyboard entry** (Settings → Controls): `Auto Secure Input` (on by default — automatic enablement when the session is in canonical-no-echo mode, the classic sudo / ssh / login password-prompt signature) and `Secure Input Indicator` (on by default). **IPC** (Settings → Advanced): `IPC Allow Send Keys` (off by default) and `IPC Allow Sensitive Sessions` (off by default). Corresponding config keys: `title-report` (`false`), `privilege-title-shell` (`true`), `clipboard-read` (`ask`) / `clipboard-write` (`allow`) / `privilege-clipboard-shell` (`true`), `auto-secure-input` (`true`) / `secure-input-indication` (`true`), `ipc-allow-send-keys` (`false`) and `ipc-allow-sensitive-sessions` (`false`).

### Progress State

The state is driven by the **ConEmu OSC 9;4** progress protocol with three feeds: programs emitting it themselves, a built-in auto-wrap list, and `otty watch`. Reporting:
```bash
printf '\e]9;4;1;40\a'   # determinate — 40 %
printf '\e]9;4;3\a'      # indeterminate — spinner (percentage unknown)
printf '\e]9;4;2;80\a'   # error — held at 80 %
printf '\e]9;4;0\a'      # clear — remove the indicator
```
| State | Sequence | Meaning |
|---|---|---|
| 0 | `OSC 9;4;0` | Clear / no progress |
| 1 | `OSC 9;4;1;<pct>` | In progress — `<pct>` is 0–100 |
| 2 | `OSC 9;4;2[;<pct>]` | Error — optionally hold at a percentage |
| 3 | `OSC 9;4;3` | Indeterminate — spinner, percentage unknown |
| 4 | `OSC 9;4;4[;<pct>]` | Paused / warning — **ignored by Otty** (no special reaction) |
| 5 | `OSC 9;4;5;<exit>[;watch]` | **Otty extension** — finished with exit code `<exit>`; the trailing `watch` tag marks a finish from `otty watch` so it can route to its own notification toggle |
These ride on the same OSC number as the OSC 9 desktop notification but are a distinct sub-protocol (the leading `4`). Try it: `otty features try progress` (determinate bar) and `otty features try error-state`.
**Automatic progress for known commands** (needs shell integration): Otty auto-wraps a built-in list of slow commands so they show an indeterminate spinner while running and a finish/error badge on exit — `curl`, `wget`, `rsync`, `scp`, `git fetch/pull/push/clone`, `brew install/update/upgrade`, `npm/pnpm/yarn/bun install`, `pip install`, `cargo build/install/update`, `docker pull/push/build`, `apt/apt-get install/update/upgrade`, "and more". Editable under Settings → Advanced → Auto Progress-Bar Commands (`progress-bar-commands`); each entry is matched as a **whitespace-delimited prefix** (`git push` matches `git push origin main` but not `git status`); clearing the field disables auto-progress entirely.
**`otty watch <cmd>`** shows an indeterminate spinner while the command runs, then a success or error badge, and posts a Notify on Watch Finish notification unless `-q` / `--quiet`; because it tags its finish with `watch`, watch notifications can stay on while noisier per-command finish notifications are off. The wrapped command's exit code passes straight through.
**Tab badges** (see also §2): Running — spinner (`OSC 9;4;1/3` in progress, or `otty watch` running); Completed — checkmark (brief success flash, then settles to Finished); Finished — accent dot (command exited 0, unread-output marker); Error — alert triangle (non-zero exit, or `OSC 9;4;2`); Awaiting input — hand (a code agent is waiting on you, or a plain command stopped at an interactive prompt); Caffeinate / Sudo (a sleep-blocking or privileged session is active, set automatically). Command-driven badges need shell integration (they key off the `OSC 133;D` exit mark) and three toggles under Settings → Shell, all on by default: **Tab Badge — When Command Finishes** (accent dot after a successful command), **Tab Badge — When Command Fails** (alert badge after a non-zero exit) and **Tab Badge — When Command Awaits Input** (hand badge when a running command stops at a `[y/n]` confirmation, a password read, or a Press ENTER to continue pause — apt, pip, ssh, installers; detection waits until the prompt has been sitting at the cursor for **about 1.5 s**, so text merely scrolling past can't trigger it, and typing into the pane clears it); the matching config keys are `privilege-badge-exit-status`, `privilege-badge-activity` and the `privilege-badge-agent-*` set. Scripts can set a badge directly:
```bash
otty tab badge --kind running        # running | completed | finished | unread | error | awaiting-input
otty tab badge --clear
```
The system-derived caffeinate / sudo badges are intentionally not settable from the CLI.
**Dock icon** (macOS) reflects aggregate progress across all tabs (Settings → Appearance): **Animate Icon on Progress** (off by default — rotates the icon's eye while any session is working, i.e. `OSC 9;4` progress/indeterminate) and **Red Icon on Error** (on by default — tints the icon red when any session reports a non-zero exit or `OSC 9;4;2`, and clicking the Dock icon jumps to the next failing tab and clears the tint); config keys `dock-icon-animate-progress` (`false`) and `dock-icon-error-badge` (`true`).
**Watching code-agent tasks.** Coding agents (Claude Code, Codex, OpenCode) report their own state over IPC — processing, idle, awaiting input — driving agent-specific badges, and these do **not** require shell integration. Under Settings → Shell the documented rows are **Claude Code — While Processing** (off by default — spinner while the agent is thinking), **Claude Code — When Task Completes** (on by default — dot when the agent goes idle) and **Claude Code — When Awaiting Input** (on by default — indicator when the agent needs approval or input). `[conflict]` The Monitor Tasks page likewise says "Badge While Processing — off by default", while the Configuration Reference gives the generic key `privilege-badge-agent-processing` default `true`. `otty watch:<agent>` blocks a script until an agent finishes: `otty watch:claude 9f3c1a2b`, `otty watch:codex <id> --timeout-secs 600`, `otty watch:opencode <id> --interval-ms 2000 -v`. Exit codes: **0** when the session reaches idle (or has since closed), **4** if the session never reported a usable state (see `--unknown-timeout-secs`), **6** if the agent has no integration installed, **9** on timeout. Hooks are read at session start, so after installing the integration the agent session must be restarted before watching it.

### Read-only Mode

Locks a pane so nothing you type reaches the shell — for protecting a long-running process's output, or handing the window to someone for a look. Toggle from the menu bar (Shell → Read Only), the command palette (type "read only", also readonly, lock, freeze, view only), or by clicking the × on the READ ONLY titlebar pill. Per-pane: splitting or opening a new tab gives a fresh editable pane. Every user-input path runs through the same gate: **keyboard input** (incl. IME commit), **paste** (⌘V, middle-click, drag-drop text), **click-to-move** (the cursor-position write some shells do), **mouse reporting** (for TUIs that consume mouse events) and **drag-and-drop of files / paths into the pane**. When an input is rejected the pane beeps once. Output from the running process is unaffected — text keeps streaming, scrollback keeps growing, and scroll/select/copy/search still work. Interaction with other modes: Vi Mode and Hint Mode temporarily hide the READ ONLY pill while they are active (their own keybindings drive selection / hinting, not the shell, so the lock isn't needed) — the lock itself stays on and the pill reappears when you exit; the Sudo / Secure Input pills are hidden while read-only is on, since none of those input paths can fire.
File panes: Read Only works on the focused file pane too, with no titlebar pill — the pane simply switches to its read-only representation. While a text pane is read-only, ⌘S / ⌘⇧S are disabled (attempting one beeps) and the info panel Status row reads **"Read-only"** instead of "Saved" / "Unsaved changes". Files opened in preview mode (PDF, images, diffs) are always read-only by nature and don't expose the toggle. How to toggle a file pane: Shell → Read Only (applies to whichever pane is focused), the command palette's **Read Only / Edit Mode** (also readonly, lock, view only / edit, editable, unlock), the workspace command palette under View Mode → **Make Read-Only / Make Editable**, or the same keybinding you set for Read Only; a Markdown / SVG / HTML pane switches to its rendered Preview while locked, while a text / code pane locks editing.

### Selection

Word selection double-click; line selection triple-click; drag selection left-click + drag; rectangular selection ⌥ + drag; extend selection ⇧ + click. ⇧←/⇧→ extend by a character and ⇧↑/⇧↓ by a line, holding ⌥ makes it rectangular; **⌘+arrows are caret moves (line start/end, page up/down), not selection**. Selected text is copied with ⌘C, or automatically per `copy-on-select`. When a program enables mouse reporting, hold ⌥ (or your bound bypass modifier) to force native selection. ⌘X cut deletes the selection on editable prompt text and falls back to a plain copy on read-only text.
Selection behaviour keys: `shift-arrow-select` (default `true`) — ⇧+arrow drives a native selection with the anchor at the current cursor (and with Copy on Select each extension copies as you go), while **⇧⌘+arrow is left untouched so it still reaches the program**; `selection-clear-on-typing` (default `true`) — the selection is dropped the moment you send any key (ordinary input, Backspace, Tab, IME commits); `selection-clear-on-copy` (UI "Clear Selection on Copy", **off by default**) — an explicit copy clears the selection afterwards and deliberately does not apply when Copy on Select is enabled; `selection-backspace-deletes` (default `true`) — Backspace with a prompt-line selection deletes the whole selection rather than one character at the cursor; off restores stock behaviour (clears the highlight, erases one character). `[conflict]` The Configuration Reference lists `selection-clear-on-copy` default as `true` while the Selection page states off by default.

### Shell Integration

Otty injects shell hooks that emit **OSC 133 (FTCS)** prompt marks, powering command outlines, working-directory tracking and exit-status indicators. Recommended default: enabled. Supported shells are **zsh, bash and fish**, auto-detected from `$SHELL`; "other shells work as terminals but don't get the integration features."
| Sequence | When | Why |
|---|---|---|
| `OSC 133 ; A` | Right before drawing the prompt | Marks prompt boundaries |
| `OSC 133 ; B` | After the prompt, before input | Distinguishes prompt from typed input |
| `OSC 133 ; C` | When the command starts running | Output begins here |
| `OSC 133 ; D ; <exit>` | When the command finishes | Records exit status |
| `OSC 7 ; file://<host><cwd>` | At every prompt | Tracks pane cwd |
Features that go dark (or fall back to a guess) without it, grouped by the mark they depend on — `OSC 133 ; C / D ; <exit>`: Outline & command navigation (the per-pane command list and jump-to-prompt); About This Line (without marks the submenu survives but offers only the pane id and the deeplink, instead of naming the command that printed the line, when it ran and how long it took); exit-status gutter dots (the green / red status marker beside each command); Tab badges — When Command Finishes and When Command Fails; command notifications & sounds (Notify on Command Finish, Notify on Error Exit, Beep on Error Exit); **on-device autocomplete learning — "only commands that exit 0 are learned"**; and re-run processes on session restore (restoring what was running needs the command-start mark). `OSC 7`: inherit working directory for new tabs, splits and windows, and auto-record visited folders (the database behind Frequent Folders — `otty jump` and Open Quickly's Folders tab). `OSC 133 ; B`: autocomplete — the ghost text and candidate panel locate the prompt from the input mark, and without it they fall back to a **~1 s timer** and lose accuracy. Injected wrappers: the edit / view / jump / learn shell functions (the Omit otty prefix option) and any custom aliases; plus SSH integration — the ssh wrapper that forwards env, installs terminfo and enables remote file/git access. Terminal bell, app notifications (OSC 9 / 777) and code-agent badges (IPC) work regardless. Turning a dependent setting on while integration is off still saves it but pops a warning.
Loading and auditing — the scripts ship readable and code-signed:
```
Otty.app/Contents/Resources/shell-integration/
├── otty-integration.zsh                       # the zsh payload (OSC 133, ssh wrapper, …)
├── otty-integration.bash
├── otty-integration.fish
├── zsh/.zshenv                                # zsh loader (ZDOTDIR entry)
└── fish/vendor_conf.d/otty-shell-integration.fish   # fish loader
```
Nothing is synthesized at runtime or written to a hidden temp file. How they reach your shell: **zsh** — Otty points `ZDOTDIR` at its bundled `zsh/` dir for the session it launches; that `.zshenv` immediately restores your real `ZDOTDIR`, runs your own `.zshenv`, then loads Otty's payload on the first prompt (so its marks win over plugin managers), and your `~/.zshrc` and other dotfiles are not edited. **fish** — Otty prepends its bundled dir to `XDG_DATA_DIRS`, fish auto-loads the `vendor_conf.d` entry, which then removes that dir again so child processes don't inherit it; your `config.fish` is not edited. **bash** — bash has no clean per-spawn auto-load, so Otty adds a small, clearly-marked block to `~/.bashrc` (and a `~/.bash_profile` shim) that sources the bundled payload only when launched by Otty; the block is inert in other terminals and removed when you turn the toggle off. **tmux is the one exception for zsh/fish**: a tmux server captures its environment once at start, so the `ZDOTDIR` / `XDG_DATA_DIRS` injection can't reach panes it later spawns; when tmux is installed Otty additionally adds the same guarded managed block to your zsh/fish rc. Turning the toggle off removes every block.
Opting out: everywhere via Settings → Shell → Provide Shell Integration (`shell-integration`, default `true`) — after a "Turn off shell integration?" confirmation Otty removes the line it added to shell startup files (the bash block and any tmux managed blocks) and stops the per-session ZDOTDIR/XDG_DATA_DIRS injection for zsh and fish. Per-shell (macOS and Linux) via the › beside the main switch, one switch each for zsh, fish and bash; the main switch follows your login shell; an ⓘ means only some shells are integrated; SSH Integration greys out when integration is off entirely. Per-shell via rc: `export OTTY_DISABLE_INTEGRATION=1` before the payload loads. Per-profile (Windows): Settings → Profiles → profile → Shell Integration writes `shell-integration = false` into the profile's own file; only PowerShell profiles carry a payload on Windows today. Per-window: `otty open --no-integration`.
Verify: `echo "marks: $OTTY_INTEGRATION"` → `marks: 1`, or watch the Outline gutter (it only renders when marks arrive). Related key: `ssh-integration` (default `true`) forwards the integration over SSH.

### Shell Menu

Shell in the menu bar is about the pane in front — four of its entries are rebuilt each time it opens: About This Line, Ports, Git, and the running agent.
**About This Line** — three ways to ask, all showing the same submenu: right-click any row in a pane and open About This Line (about the row you clicked), Shell → About This Line, or About This Line... in the Command Palette; the last two have no click to go on, so they read the line the caret is on — or the first line of the selection, when there is one. What the submenu says: the command that printed the line with the time it ran (click that row to scroll back to the command itself), how long its output took and how it exited, the pane id (click to copy), and Copy Deeplink. Only the last two items appear when the line has no command behind it (a pane without shell integration, or output printed before the first prompt). On the alternate screen (vim, htop, less) there is no scrollback line to point at, so the submenu drops the line and offers a link to the pane instead.
**Deeplinks** — `otty://pane/p_19e630f19fe_21?line=1204`. Opening one raises that window, switches to that tab, focuses that pane and scrolls that line into view with a brief highlight. `otty pane link` prints one. The line number is the pane's current scrollback position, so it drifts after buffer overflow or a re-wrapping resize and means nothing after the pane closes.
**Ports** — listening TCP ports listed by terminal when the menu opens, each row showing its port number and process name (e.g. `5173 node`); ports belonging to other applications or detached servers appear under Other; Otty filters out its own listener and OS services. Discovery is passive (process/socket information only — no connecting, no HTTP requests, no title fetches), and the command palette uses the same passive discovery. Open in Browser opens `http://localhost:<port>`; the list includes non-web services (debuggers, databases) so only use it for web servers; a port bound by several tabs appears under each of them. **Windows** has `Shell → Listening Ports...`, a dialog rather than a submenu; **the Linux app does not offer this yet**.
**Git** — the branch with `(worktree)` after it when in a linked worktree, then: Commit... (commit sheet for the changes), Create Branch... (asks for a name and branches from where you are), Push / Pull / Fetch (confirms, then runs it), Merge... / Rebase... ### $TERM and Identification

`term = auto` (default) — **`auto` resolves to `xterm-256color`**, a deliberately conservative choice present on every Unix terminfo install and enough for line editors; truecolor is advertised separately through `COLORTERM`, so 24-bit color is not lost. Setting `term` to any other value makes Otty check that a matching terminfo entry exists first; if it doesn't, Otty logs a warning and falls back to `xterm-256color`. The docs carry an explicit warning against `term = xterm-kitty`, `term = xterm-ghostty` or another terminal's name — "TERM selects a capability database, not a behaviour".
Identification variables exported into every child process:
| Variable | Value | Purpose |
|---|---|---|
| `TERM` | `xterm-256color` (default) | terminfo capability database |
| `COLORTERM` | `truecolor` | Advertises 24-bit color |
| `TERM_PROGRAM` | `otty` | The canonical "which terminal am I in?" probe (recommended for scripts/prompts; stable across `term`, survives tmux, no escape parsing) |
| `TERM_PROGRAM_VERSION` | build version | Paired with `TERM_PROGRAM` for version gating |
| `CW_TERM` | `otty` | Stops Amazon Q / Fig / CodeWhisperer from exec-ing `cwterm` mid-`.zshrc` (which would suppress shell-integration marks) |
| `OTTY_PANE_ID` | per-pane id | Identifies the pane a process runs in; pass to `otty pane show --pane "$OTTY_PANE_ID"` (or send-keys/capture) to act on the caller's own pane |
Example probe: `echo "$TERM_PROGRAM ($TERM_PROGRAM_VERSION), TERM=$TERM, COLORTERM=$COLORTERM"` → `otty (1.0.2), TERM=xterm-256color, COLORTERM=truecolor`.
**Device attributes** (answered synchronously over the PTY): DA1 (`CSI c` / `CSI 0 c`) → `CSI ? 6 c` ("I'm a VT102-class terminal"); DA2 (`CSI > c`) → `CSI > 0 ; <version> ; 1 c` (model ID 0 generic, build version, ROM slot 1), where `<version>` = `major × 10000 + minor × 100 + patch` with any `-rc`/`-beta` suffix dropped (a 1.0.2 build reports `10002`), matching xterm and Alacritty encodings. **DA3 (tertiary attributes) is not implemented — Otty sends no reply**, the correct behaviour for an unsupported query.
**XTVERSION** (`CSI > q`, used by nvim, kakoune and others to gate undercurl, truecolor and the Kitty keyboard protocol) → `DCS > | otty(<version>) ST`, transmitted as `ESC P > | otty(<version>) ESC \`, terminated with `ESC \` (7-bit ST) so it survives 8-bit-clean PTYs, with the plain build version string (e.g. `otty(1.0.2)`).
**Cursor and status reports**: `CSI 5 n` → `CSI 0 n` (ready/OK); `CSI 6 n` → `CSI <row> ; <col> R` (1-based cursor position).
**terminfo** — Otty ships precompiled entries inside `Otty.app/Contents/Resources/terminfo/` and splices that directory to the front of `TERMINFO_DIRS` for every shell (so `xterm-ghostty`, alacritty and friends resolve even if never installed; the bundle path is searched first, and `/usr/share/terminfo` is appended so nothing else is hidden). Over SSH the ssh wrapper checks on first connection whether the remote can already resolve your `TERM`; if it can, nothing is installed; only otherwise does Otty extract the entry with `infocmp`, pipe it over, and compile it with `tic` into `~/.terminfo`. The result is cached per `user@host`, and connections carrying a remote command (`ssh host 'some command'`) skip the check entirely.
**Cleaning up entries left by Otty 1.3.0 and earlier**: through 1.3.0 that check was broken and installed the entry anyway, under the standard name, on every host you ran a remote command against, shadowing the (usually newer, more complete) distribution entry and changing what Backspace and mouse reporting look like remotely. `otty ssh terminfo myserver` reports which capabilities come back and which values change; `otty ssh terminfo --clean myserver` **moves** it into `~/.terminfo-otty-backup` on that host (moved, not deleted). A host whose only entry for that name is the one in `~/.terminfo` is never touched. Related: `enquiry-response` (reply for ENQ 0x05), `osc-color-report-format` (`16-bit` default; `none`, `8-bit`, `16-bit`), `title-report` (`false`), `vt-kam-allowed` (`true`), `login-greeting` (`false`).

### Unicode and Text Styles

Rendering is on the GPU — **Metal on macOS, DirectX 12 on Windows** — with each glyph cached so it is rasterized once and reused. Otty handles the whole Unicode range **U+0000–U+10FFFF**, not just the BMP: combining marks stacked over a base glyph (accents, diacritics, Hangul jamo); wide East Asian characters — CJK ideographs, kana and full-width forms — each occupying two cells, so table and TUI column alignment stays correct; and right-to-left text (Hebrew, Arabic) reading correctly out of the box via `bidi` (on by default), while pure LTR content is left untouched. **Emoji**: color emoji render in full color using the system emoji font (Apple Color Emoji on macOS, Segoe UI Emoji on Windows); multi-codepoint sequences collapse into one glyph across two cells — ZWJ families (👨👩👧👦), profession and skin-tone modifiers (👋🏽, 🧑💻) and flags (🇯🇵); and variation selectors are honored, so a character can request its text (▶︎) or emoji (▶️) presentation. **Nerd Font icons**: an embedded font is used automatically for Private Use Area glyphs, covering both families — **Classic Nerd Font** icons in the BMP PUA (Powerline separators, file-type and Git-status symbols, and the glyphs in prompts like Starship and Powerlevel10k) and **Material Design Icons** (the large `nf-md-*` set in a supplementary PUA plane, including the folder, file and device glyphs yazi, lsd and eza print).
**Wrapped CJK lines** — when a wide CJK character cannot fit in the last column some line editors (zsh) pad that column with a reverse-video space and wrap; the pad is a real cell and shows as a small solid block stranded at the right edge. `strip-cjk-wrap-pad` (default `false`, Settings → Advanced → All Settings) hides that one isolated cell; for Otty's bundled zsh it also tells zsh not to emit the pad (still overridable from your own `.zshrc`). Off renders it verbatim, the same block tmux, Ghostty and Terminal.app show. It only ever affects a lone reverse-video space at a soft-wrap boundary.
**Ambiguous-width characters** — of the East-Asian-Ambiguous blocks, "by default Otty widens the enclosed alphanumerics block (① ② ③ ⒶⒷ ⓐⓑ) to two cells, which fixes the most common misalignment on macOS without disturbing arrows, box-drawing, or Powerline glyphs". More blocks can be widened (number forms, math operators, technical symbols, dingbats, arrows, geometric shapes) via `widen-ambiguous` / Settings → Advanced → Widen East-Asian-Ambiguous Blocks; only enable a block if your font actually draws it at two cells of advance, and **changes apply to newly opened tabs**. `[conflict]` The Configuration Reference gives `widen-ambiguous` default `(empty)` with "Empty by default so widths match your shell's wcwidth".
**Ligatures** — for fonts that ship them (Fira Code, JetBrains Mono, Iosevka, Cascadia Code, …) Otty shapes programming ligatures so `=>`, `!=`, `>=` and `->` join into a single glyph, by default only on symbol runs, leaving letters and digits untouched. `font-ligatures` (`off` disables programming ligatures, `calt` enables the standard/contextual set, `dlig` also enables discretionary ligatures); `font-ligatures-alphabet` (default `false`) applies them inside runs of letters/digits/CJK. Chosen from Settings → Appearance → Text. `[conflict]` The Fonts page lists the same three values and states "**off** — no ligatures (default)", while the Configuration Reference gives `font-ligatures` default `dlig`.
**Icons (Nerd Font)** — an embedded Nerd Font is used automatically for Private Use Area icon glyphs with no install or configuration; both icon families are covered. An icon drawn wider or taller than a cell is scaled to fit and centered. A user-installed patched Nerd Font added as a `font-family-fallback` takes precedence for those codepoints.
**Text styles** (all rendered): Bold (font's real bold face), Italic (real italic face), Dim/faint (reduced intensity), Underline (single, double, curly/undercurl, dotted, dashed — with an underline color independent of text color), Blink (slow and rapid), Strikethrough, Reverse/inverse (fg↔bg swap), Color. Underline shapes map to typical uses: single = links/plain; double = emphasis; curly = spell-check/diagnostic squiggles (nvim, VS Code in the terminal); dotted = hint/info diagnostics; dashed = warnings. `text-underline` (default `true`) — turning it off affects only SGR underlines; link underlines (⌘-hover / OSC 8) and strikethrough are unaffected. `text-blink` (default `false`) — SGR 5/6 cells render steady when off, blink at **about 1 Hz** when on (off by default because blinking is an accessibility concern and is more often emitted by accident). `text-bold` / `text-italic` (both default `auto`; values `off`, `auto`, `primary-only`, `synthetic`) decide how bold/italic cells resolve when no real face exists. How aggressively Bold/Italic/Underline/Blink are honored is adjustable from Settings → Appearance → Text.
**Color depth** — 24-bit truecolor (16.7 million colors), 256-color, and the standard 16-color palette; truecolor and 256-color are advertised automatically through `TERM` and `COLORTERM`.
**Rendering tuning** — `font-blending` (default `srgb-over`; `srgb-over`, `macos-like`, `linear`, `perceptual`; aliases `font-smooth`, `font-antialiased`); `windows-text-rendering` (**Windows only**, default `natural`; `natural`, `natural-symmetric`, `gdi`, `cleartype`, `aliased`); `font-thicken` (**macOS only**, default `false`, auto-enabled when `background-opacity < 1.0`); `arrow-box-drawing-join` (`true`); `adjust-cell-height`; `minimum-contrast`; `bidi`; `text-blink`; `terminal-scroll-smooth`.

### Vi Mode

Navigate scrollback and select text with vi-style keys. **Status: supported in terminal panes, not supported in Otty's built-in code editor yet.** Enter with ⌃⇧Space (Control-Shift-Space); show/hide the key-hint bar with ⌘/; leave with Esc or q (or the × on the pill). In Vi Mode the terminal stops forwarding keys to the shell — they drive the cursor through scrollback instead. Remappable under Keybindings (command `Vi Mode`); a separate **Mark Mode** command (no default binding) enters the same mode with an arrow-key + Shift-select emphasis. Any motion can be prefixed with a count (`5j`, `3w`, `10k`), and the pending count shows in the Vi Mode pill.
Motions: `h j k l` left/down/up/right; `w b e` word forward/back/end; `0 $` line start/end; `^` first non-blank; `H M L` top/middle/bottom of screen; `g g` / `G` top/bottom of scrollback; `⌃u` / `⌃d` half-page up/down; `⌃b` / `⌃f` full-page up/down. Arrow keys mirror hjkl so Mark Mode works without the letters.
Selection: `v` character-wise visual; `V` line-wise visual; `⌃v` block (rectangular) visual; `o` swap the cursor to the other end; `y` yank to clipboard (exits Vi Mode); Enter copies the selection and exits.
Search: `/` forward and `?` backward open the find bar to type a query; Esc hands focus back to the buffer, then `n` / `N` step the vi cursor through matches (`n` in the search direction). `f` enters Hint Mode. **Vi Mode has no config-file keys** — remap the Vi Mode, Mark Mode and Vi Mode Key Hints commands under Keybindings.

### VT sequence tree

The vendor `vt/*` tree is in `spec/corpus/vt/` (73 pages; sitemap 142). Index: `spec/corpus/vt/sequence-reference.md`. Machine-readable Otty-column table: `spec/vt-sequences.md` / `vt-sequences.json` (106 entries). Marks: ✓ implemented, ◐ partial, ☐ / ❌ not yet. Overview: Otty's terminal core is forked from **Alacritty's** VT parser; behavior matches **DEC VT520** + modern **xterm** where they disagree. Categories: C0/Fe, ESC, CSI, OSC, DCS/APC/PM. ST is `ESC \` (preferred) or BEL (legacy). Sequence-reference notes not already in this section: CSI 6 n DSR is ◐ (DECXCPR `CSI ? 6 n` not implemented); CSI XTWINOPS is ◐ (14/16 t pixel sizes answered, 18 t chars intentionally not, window-acting ops ignored); OSC 5 ✓ parsed (underline applied); OSC 13/14 ✓ parsed (no macOS effect); DCS DECRQSS other targets ❌; XTGETTCAP ❌; Sixel ☐ planned; tmux passthrough ◐.
**OSC 88 — Terminal Resume Protocol** is a *proposal* (v1; Otty ships the reference implementation; spec at `github.com/Otty-sh/osc-88`), gated by the Terminal Resume Protocol setting (on by default). Wire: `OSC 88 ; <op> [ ; <key>=<value> ]... ST` with ops `arm` / `clear`; values are base64 UTF-8; unknown keys ignored. `arm` fully replaces the prior spec (last-write-wins) with `cmd` / `args` / `self_repaint`; `clear` withdraws it. Emit to `/dev/tty` (or `otty resume:arm --cmd … --args …` / `otty resume:clear`); a clean `clear` so a deliberate quit is not resurrected, a crash (no `clear`) leaves it armed. On cold restore Otty re-runs `cmd` + `args` in `cwd`; `self_repaint=1` skips that pane's visual log replay so the program redraws itself. Full page: `spec/corpus/vt/osc__osc-88.md`.

## 4. Agent integration

Otty plugs into agent CLIs you run yourself; it does not run them for you. Installation is one click per agent: the first time Otty needs an integration it asks to install the hook/plugin into that agent's own config, touching nothing else in the file, and the switch can be turned back off to remove Otty's entries cleanly. The integration connects only after the agent restarts with the new config (for OpenCode, send one message so the plugin reports the session; for Codex, if you recently updated Otty or Codex, approve the trust prompt when it restarts).

Recovered per-agent mechanics (the exact resume / fork command, plus prerequisites and quirks):
- **Claude Code** — resume `claude --resume <id>`; fork `claude --resume <id> --fork-session`; transcripts JSONL under `~/.claude/projects/…`.
- **Codex** — resume `codex resume <id>`; fork `codex fork <id>`; Codex only runs hooks when the hooks feature is enabled in `~/.codex/config.toml` — Otty turns it on when it installs them and offers a one-click re-enable if it ever gets switched off (then restart Codex in that tab).
- **OpenCode** — resume `opencode --session <id>`; fork `opencode --fork --session <id>`; the plugin needs **OpenCode 1.3.4 or later** (Otty asks to "Update OpenCode Plugin" → click Update and restart); OpenCode doesn't announce a session when you switch to it via `/sessions`, so a freshly-switched tab links up once you send a message in that session.
- **Cursor CLI** — resume `agent --resume <chatId>`; **Fork is not offered** (Cursor has no CLI fork command, so the action stays greyed out); transcripts under `~/.cursor/projects/…/agent-transcripts/`.
- **Kimi Code** — resume `kimi --session <id>`; **Fork is not offered**; sessions under `~/.kimi-code/sessions/…`.
- **Pi / omp** — resume `pi --session <path>` (`omp --session <path>`); fork `pi --fork <path>`; like OpenCode they report the session id through the extension, so a freshly-switched tab links up on the next lifecycle event.
- **Grok Build** — resume `grok --resume <id>`; fork `grok --resume <id> --fork-session`; **session history isn't wired up yet**, so Grok sessions don't appear in History or Open Quickly; because the shared `~/.claude/settings.json` file can be started by either agent's runner, each Otty hook there checks who invoked it and stands down when it isn't the right agent; Grok must trust a folder before it runs any hook in it (it asks the first time; `/hooks-trust` does it by hand) — until you accept, the tab shows no badge.
- **Reasonix** — resume `reasonix --resume <id>`, and run it from the same project directory (it looks the conversation up in the session store of the directory you started in); fork `reasonix --resume <id> --copy`, leaving the original transcript alone; it also reports awaiting-approval, so the awaiting-input badge works; hooks load when a session starts (restart reasonix after installing); `settings.json` is shared with Reasonix's own Hooks editor, so Otty won't rewrite it if it can't read it — if Install won't stick, the file has a syntax error; **session history isn't wired up yet**.
- **CodeBuddy CLI** — resume `codebuddy --resume <id>`; after installing hooks, open CodeBuddy's `/hooks` panel to review and activate external changes; on Windows CodeBuddy runs its hooks through Git Bash.
- **Google Antigravity CLI** — resume `agy --conversation <id>`; Otty does not install tool permission decision hooks for Antigravity.
- **GitHub Copilot CLI** — resume `copilot --resume <id>`; the integration targets GitHub's standalone coding agent CLI.

History discovery covers Claude Code, Codex, OpenCode, Cursor, Kimi, pi and omp, including Codex's `CODEX_HOME` and Kimi's `KIMI_CODE_HOME` overrides. Linux and Windows expose session and prompt history through Open Quickly. Session usage follows the table; plan quota is available for Claude, Codex and omp. Claude's plan file can be opened from the agent actions. *Quota* is the plan's remaining allowance, answerable only by Claude Code, Codex and omp; Otty runs that agent's own CLI in the background — `claude -p "/usage"`, `codex app-server`, `omp usage --json` — every few minutes, using the login the CLI already has. It re-reads **every 5 minutes** and again whenever a task finishes; several agents finishing at once still costs one reading; if the CLI isn't installed Otty stops after a few failed attempts. Claude's probe runs on the cheapest model, at low effort, with session persistence off (so it neither shows up in session history nor costs anything meaningful). No sign-in, no stored password, nothing read from the Keychain.
**Bars need a real ceiling.** Codex is the only agent that states one (its context window goes into its own session log, and its plan window comes back from the server), so both of its readings get a bar — **amber past 75%, red past 90%**; every other agent shows raw measured occupancy because a ceiling would have to be guessed from a model id (Claude in particular records nothing distinguishing a 200k session from a 1M one). Codex's quota is asked for, not overheard: it now queries `codex app-server` rather than the frozen `rate_limits` block in its session log. Per-agent quota bars: **Claude Code** shows *Session quota* and *Weekly quota* bars, each with its reset time underneath — the same two numbers `/usage` shows inside Claude Code, from `claude -p "/usage"`; **Codex** shows its plan's window plus any per-model allowance as separate bars, since they are separate budgets, asked of `codex app-server` directly so the figures are live and include usage from your other machines; **omp** gains its 5-hour, weekly and monthly spend limits from `omp usage --json`, pooling every account you have signed in into one bar the way omp's own capacity line counts them, and covering spend omp itself brokered (the "As observed by omp" line).
**Cost is only ever the agent's own number** — OpenCode, pi and omp compute and write what a session spent; the others log tokens but no cost, and pricing those against a public rate card would produce a misleading API-equivalent figure, so nothing is shown.

**Keeping the Mac awake** — "Prevent Sleep While Processing" holds macOS awake while an agent works, and releases it the moment the agent goes idle; per-tab (only tabs with a processing agent and the toggle on hold the assertion). A MacBook with the lid shut sleeps anyway; overriding that (`Also When the Lid Is Closed`, off by default, behind the disclosure on that row) needs a system-wide setting only root can write, so switching it on first installs a small background helper the user must approve in System Settings → General → Login Items & Extensions → App Background Activity. **Otty has to be in the Applications folder** for that helper. The hold lasts exactly as long as the task and is tied to the live connection to the helper rather than to anything on disk — quitting, force-quitting or crashing hands normal sleep straight back. Turning the switch off leaves the helper in place, so re-enabling needs no second approval.
**Skills** (Settings → Agents → Skills card; full page `spec/corpus/skills.md`). Copy a row, then paste into your agent — what you paste is an *installer prompt*, not a file; the agent writes the skill wherever that agent keeps skills (Claude Code, Codex, OpenCode, …) so Otty does not need each layout. Nothing is written to disk behind your back. The dialog asks for a name first (that name is the slash command, the file and the install path together); rename `wait` to `otty-wait` if it would collide. Some agents need a fresh session before the new slash command appears. Four skills:
- `/wait` — block until a session id, a pane id, or a described thing ("the build in the other tab") is idle. Agent panes idle when the *agent* reports idle; shell panes when the command has exited and the prompt is back. Underneath: `otty pane wait` and `otty watch` (blocks, does not poll).
- `/tell` — send a line to a session, pane, tab, or window. Addressed to an agent it lands in that conversation; addressed to a shell pane it is typed at the prompt. Off by default (`ipc-allow-send-keys`); the **/tell** dialog carries the switch; installed without it every send is refused. SSH and Read Only panes refuse regardless.
- `/open` — put a file or URL on screen (`in a split` / `in a new tab` / `in a new window`; default new tab). Files open in the file pane with highlighting; URLs in the built-in browser. You do not have to name a CLI placement.
- `/otty` — the four-in-one workspace skill (opens panes, runs, captures, starts a second agent, waits, closes what it opened). Needs the same type-into-panes switch. See Orchestration below.
**Orchestration (`/otty` skill).** `/otty` teaches an agent Otty's whole workspace, composing the single-verb skills:
| The agent can | Using |
|---|---|
| See every window, tab and pane, and which agent sits in which | `otty pane list` |
| Open a pane beside itself, at a size, in a directory | `otty pane split` |
| Run a command there and get its exit code — or its output | `otty pane run` / `exec` |
| Read what is on a screen, including a TUI or a pager | `otty pane capture` |
| Start a second coding agent and give it a task | `split --command` + `send-text` |
| Block until a build, a pane, a tab or another agent is idle | `otty pane wait` / `otty watch:<agent>` |
| Tidy up the panes it opened | `otty pane close` |
Nothing is simulated and there is no daemon to start. Install it from Settings (⌘,) → Agents → Skills → Copy, leaving the switch **Allow agents to type into panes** on — without it every `send-text` is refused and the multi-agent half of the skill fails on first use — then paste it into your agent; the agent picks the skill by reading its description when you say something like "run that in a split", and the name is yours to change before copying (e.g. install it as `otty-drive`). Hand-driving example:
```bash
otty pane split --direction right --cwd "$PWD" --no-focus --json
otty pane run --pane p_19f0bfe5ce9_1a -- cargo test
otty pane wait --tab t_19f0bfe5ce9_1a --timeout-secs 600
otty watch:claude 226dd916-67cb-443c-ae87-04d5b6761a9b
```
**Permission:** typing into a pane is off by default — the `/otty` dialog carries the switch (`ipc-allow-send-keys`), also Settings → Advanced → IPC Allow Send Keys; everything else (splitting, running, capturing, waiting) works without it. **Completion signals:** a shell pane reports through Shell Integration (OSC 133) — the terminal knows when a command started and finished, so `otty pane wait` returns on the fact rather than on a timer; an agent pane reports through the agent's own lifecycle hook, which matters because an agent owns its terminal for its whole life and a shell-level view of it would read "busy forever" — `otty watch:claude <session>` returns when the agent says it is idle. Where a pane can report neither, `wait` exits immediately and says so rather than hanging, and the skill is told to report that verbatim instead of falling back to a sleep — the missing piece is almost always an agent integration that was never installed, or one installed after the session started. Limits the skill cannot turn off: panes in an SSH session or in sudo mode refuse typed input unless **IPC Allow Sensitive Sessions** is additionally enabled; the skill is instructed to close only panes it opened itself and never the one it is running in (closing that would end the conversation with it); and every pane it opens is opened without stealing focus, so work appears beside you rather than yanking you out of what you were typing.
**Custom agents.** Any agent that can run a command when a turn starts and ends plugs into the same UI: `otty state:myagent state=processing agent-pid=$$ session-id=abc123 label="My Agent"` and `otty state:myagent state=idle …`. The name after `state:` is the agent id; an id Otty ships an adapter for gets the full integration, any other id is a custom agent that drives the lifecycle badge and notifications under the name it reports and nothing else. The `otty` command must be on `PATH` (Settings → Shell → Install CLI).
| Argument | Required | Meaning |
|---|---|---|
| `state=` | yes | `processing` — a turn just started · `idle` — the turn finished · `awaiting` — waiting for approval or input · `error` — the turn failed |
| `agent-pid=` | on the first event | PID of the agent process, used to pin the event to a pane. In a hook script `"$PPID"` is the agent that invoked it |
| `session-id=` | recommended | A stable id for the conversation; once a pane has seen it, later events carrying the same id land on that pane even without `agent-pid` |
| `label=` | optional | Display name for badges and notifications; defaults to the capitalized id (so `state:myagent` reads as "Myagent") |
Pane matching is by process tree: the reported `agent-pid` must be a descendant of some pane's shell — an event whose pid belongs to no pane is dropped, so the same agent running outside Otty never badges an unrelated tab. Built-in agents also have a cwd + process-name fallback; a custom agent has none, so its first event must carry `agent-pid` or the call reports that no tab was found. A custom agent gets the processing / awaiting / done tab badges and the Dock progress spinner, system notifications when a task completes and when the agent starts waiting for you, correct ordering under **Updated Time** tab sorting, and keep-awake while a turn runs — all honouring the same per-tab switches, so a tab whose agent badges or notifications are turned off stays quiet. **Resume, Fork and History stay adapter-only**, because they need Otty to know how to relaunch the agent and where it stores transcripts — neither of which a state report can carry. Bundled hooks have this shape:
```sh
#!/bin/sh
# $1 = processing | idle | awaiting
otty state:myagent \
  state="$1" \
  agent-pid="$PPID" \
  session-id="$MYAGENT_SESSION_ID" \
  label="My Agent" 2>/dev/null &
```
An agent can adopt **Terminal Resume Protocol (OSC 88)**, a vendor-neutral open spec, to get resume in Otty without a bespoke integration.
**Agent History viewer.** Agent session logs render as a readable transcript instead of raw JSON, recognized by session path:
| Agent | Session files |
|---|---|
| Claude Code | `~/.claude/projects/<project>/*.jsonl` |
| Codex | `~/.codex/sessions/YYYY/MM/DD/*.jsonl` |
| OpenCode | `~/.local/share/opencode/storage/session/<project>/*.json` |
| Cursor CLI | `~/.cursor/projects/<project>/agent-transcripts/<chat>/<chat>.jsonl` |
| Kimi Code | `~/.kimi-code/sessions/wd_<project>/session_<id>/agents/<name>/wire.jsonl` |
| Pi / omp | `~/.pi/agent/sessions/<project>/*.jsonl` (omp: `~/.omp/...`) |
The transcript lays out user and assistant turns with Markdown-rendered text, tool calls, reasoning and attachments; you can select and Copy or Send to Chat, and a **Resume** button in the toolbar continues that session — jumping to the live tab if it's still running, otherwise spawning a fresh one with the agent's `--resume`. Only session files under a known agent's directory auto-open as a transcript; any other `.jsonl` stays plain text. History opens from the Command Palette or the titlebar dropdown; Open Quickly's Agents filter (⌘G) searches sessions across all supported agents, ↩ resumes, ⌘K offers more (including Branch / Fork in New Tab and View Session History). A resumed session keeps the original provider, model and system prompt — only the conversation continues. Viewer actions: select content and Copy or Send to Chat from the context menu; a **Resume** button in the toolbar; **right-click → View as → `<Agent>` History ⇄ JSONL (Syntax Highlight)** to drop back to the raw log; and document-style keyboard scrolling (Page Up / Page Down, Home / End, arrow keys nudge a line, Space / Shift-Space page through).
**Fork / Branch.** A GUI action — no slash command. Otty labels it after each agent's own term: **Branch for Claude Code, Fork for Codex and OpenCode** (the command-palette picker uses the focused agent's terminology). Forking copies a session's history up to the current point into a fresh session; both stay live. The copy resumes the original context — same provider, model and system prompt — and only the future diverges. Under the hood Otty runs the agent's native resume-and-fork command (for Claude Code, `claude --resume <id> --fork-session`), so the new pane is a real independent session that can itself be kept, resumed or forked. Install the agent integration first — Otty can only fork a session it can identify, which needs the hook/plugin from Setup, and if it is missing the fork action offers to install it on the spot. Focus a running agent pane, then trigger `Branch in…` / `Fork in…` from the Details Panel Info tab (⌘⇧R), the Command Palette, or Open Quickly → Agents filter (highlight a session, press ⌘K), and choose where the copy lands: Split Right / Left / Down / Up, New Tab or New Window.
**Composer** — the agent input affordance: multi-line, cursor operations, undo/redo, float-on-top, rich paste (⌘V converts HTML, RTF or images on the clipboard into Markdown; ⇧⌘V pastes plain text). ⌘↩ sends and clears the draft; both ↩ and ⇧↩ insert a newline, so multi-line is the default; Esc cancels but preserves the draft; the composer grows to a configurable maximum height before scrolling internally. It lives in the same pane as its agent, so by default it closes when you switch to a tab that doesn't hold that pane (draft stashed and restored); **pin** keeps it visible across tab switches and is remembered as a preference. **Pop-out** detaches it into a floating Spotlight-style panel that stays on top without activating Otty or taking over the menu bar; the draft (text and inline attachments) moves with it, and send or close docks it back. **⌥⌘↩** (or the queue button) routes the draft into the pane's Prompt Queue instead of sending — each non-blank line becomes a separate queued command.
**Send to Chat** — attaches terminal output, file-pane selections or shell context to the active (or a new) agent session without copy-pasting: select text in a terminal or file pane (or just focus the pane for "last output" — that half is what shell integration enables), then **right-click → Send to Chat, or ⌘⌃↩**, then pick a target (the active agent session, or New session). The content lands as a quoted context chip above the composer — review it, add your question, and send. If no agent session is open it starts one; if several are running a small picker chooses the recipient, with the last-used session as default. The Composer also supports `@` file references for a more targeted attach.
**Prompt Queue** — see §3 Input for mechanics; each queued line fires at the next idle prompt, in order, gated on shell integration.
**Monitor Tasks** — per-tab, so a long background task can badge and notify while a tab you're watching stays quiet: **Tab Badge** (clears automatically when you focus the tab; Clear Badge removes it manually), **Notification** (system notification when a tab isn't visible or Otty isn't frontmost; respects macOS Focus/Do-Not-Disturb and is delivered through Notification Center, so clicking one returns to the right tab), **Keep macOS awake** (per-tab), **Queue next command**.

## 5. Workflows

**Recipes.** A portable snapshot of repeatable work — text snippets, or a whole workspace of tabs, panes, working directories and optionally the commands run. Saved recipes live in an internal database (`~/.config/otty/recipes/`) and appear in Settings → Recipes, the File → Recipe menu and the command palette (Apply Recipe). Saving is ⌘S on macOS / **Ctrl+Shift+S** on Windows (or File → Recipe → Save…): arrange the tabs and splits, then give a Name, choose a Scope, leave Content on Layout Only and hit Save. To hand a recipe to someone else, export it as a standalone file with ⇧⌘S / **Ctrl+Shift+Alt+S** — see the `.ottyrecipe` file. Scope and content level:
| Scope | What it saves |
|---|---|
| Current Tab | Just the focused tab, including its split panes |
| Current Window | Every tab in the window |
| (Commands scope) | A list of commands only — creates no tabs or windows; opening it replays them into the currently focused pane |
| Content level | What's stored |
|---|---|
| Layout Only | The pane tree and each pane's working directory |
| Include Scrollback | The above, plus each pane's scrollback, restored on open |
| Include Commands (replay on open) | The above, plus the commands to re-run when the recipe opens |
Command history comes from shell integration (OSC 133 command marks), so replay only works where integration is active; each pane keeps its most recent commands, and commands that were themselves restored from an earlier recipe are skipped so replays don't compound. For the **Commands** scope Otty lists the focused pane's recent commands oldest-first; tick the ones to keep (Select All toggles the whole list, and you can double-click a row to edit its text) and Save stays disabled until at least one command is ticked. **Include Scrollback is kept only in internally-saved recipes — exported `.ottyrecipe` files leave scrollback out to stay small and diffable.** Exports carry no scrollback, machine-local shortcuts or agent sessions — just layout, paths (with portable variables preserved) and commands; ⇧⌘S / Ctrl+Shift+Alt+S exports a standalone file. Portable paths: turn on **Make paths portable** in the save panel to replace an absolute prefix with `{{current_folder}}` (the directory you open the recipe from), `{{home}}`/"Home Folder" (`~`) or `{{recipe_location}}` (the folder containing the `.ottyrecipe`).
Opening: double-click a `.ottyrecipe` in Finder (new window populated from the recipe), `otty open foo.ottyrecipe` (same), or File → Open Recipe (picks from the internal DB). Format is a single TOML document:
```toml
[recipe]
name = "deploy-prod-debug"
version = 1
scope = "window"          # "tab" | "window" | "commands"

[[window.tabs]]
title = "API"

[[window.tabs.panes]]
cwd = "{{current_folder}}/api"
commands = ["tail -F log/prod.log"]

[[window.tabs.panes]]
cwd = "{{current_folder}}/api"
split = "right"           # relative to the previous pane
size = 0.5                # 0.0–1.0 of the parent
commands = ["make deploy"]
```
**Command replay security** — modes: `Auto` (all commands run automatically, in order), `Ask Once` (commands are shown in the pane; press Enter once to run them all), `Manually` (fed one at a time — press Enter to run each and the next appears), `Skip` (layout only). Internally-saved recipes are trusted implicitly; the first time a `.ottyrecipe` Otty hasn't seen is opened, every command it will run is shown grouped by tab and pane before anything executes, with three choices: **Always Trust** (remember this file by SHA-256 hash and run by your replay setting from now on), **Run Once** (run this once by your replay setting; ask again next time) or **Cancel** (open nothing). Editing the file changes its hash, so a modified recipe counts as new and prompts again. Trusted files are recorded in `~/Library/Application Support/Otty/trusted_recipes.json` (`%LOCALAPPDATA%\otty\trusted_recipes.json` on Windows). Commands that hand off the shell (`ssh`, `tmux attach`, `docker exec -it`, `su`, …) are recognized and, in Auto / Ask Once, stop the replay after such a command instead of blasting the rest into a not-yet-ready remote shell; the remaining commands wait until the inner shell is back at a prompt or for manual continuation, and Otty "deliberately errs toward pausing too often rather than too rarely". `[conflict]` The Recipes page states defaults "Saved Recipes → Auto (you wrote them), Recipe Files → Ask Once", while the Configuration Reference gives `recipe-replay-saved` default `ask_once` and `recipe-replay-file` default `manually`, and lists only three values (`auto`, `ask_once`, `manually`) against the page's four (which adds `Skip`).
**Text snippets.** Reusable text expanded by typing a short alias at the prompt (created in Settings → Recipes → Add → Text Snippet, whose three fields are **Name** — the list label — **Alias** — the trigger you type, no spaces because the shell would split on them — and **Text** — the body that gets sent; the alias is accepted from the autocomplete panel, Otty erases what you typed and sends the expanded body). Placeholders: `{{clipboard}}` (current clipboard text), `{{date}}` (today's date, `YYYY-MM-DD`), `{{time}}` (current time, `HH:mm`, 24-hour), `{{cursor}}` (where the cursor lands after sending — honored once per snippet). Example: alias `gco`, body `git checkout {{cursor}}`. The docs note aliases of a shell may cover most use cases.
**Session recovery.** ⇧⌘T reopens the last closed tab, pane or window, restoring it into the window it came from; history persists across app launches, Otty keeps the **last 12 closed items**, and File → Open Recent separately lists the **10 most recent sessions and folders**. Launch restores the previous session automatically — there is no "do you want to restore?" dialog. What you get depends on how the last session ended: **after a clean quit** it is governed by `on-launch` (the default `restore_session` reopens every window from your last session with its tabs, splits, working directories and scrollback; `new_window` always starts with one empty window); **after a crash or force-quit** the last snapshot is always restored regardless of `on-launch`, and if Otty crashes repeatedly on launch it stops auto-restoring after a few attempts and starts fresh to break the loop; **after an in-place update** relaunching always restores, so updating never costs you your layout. `[conflict]` The same page's Crash recovery section instead says the next launch *offers* to restore your open windows from the last known snapshot. What comes back is governed by Settings → Shell → Session Restore: `session-restore-multiplayer` (default `true`, "Restore Multiplayer") reattaches a multiplexer session (tmux today) instead of opening a fresh shell; `privilege-resume-agent-session` / "Restore Code Agents" (default `true`) resumes the Claude / Codex / OpenCode session the pane was running. Re-running commands: `session-restore-processes` (default `none`) — `None` (nothing is re-run; just the shell and its directory), `Whitelisted only` (a command is re-run only if it matches the Command Whitelist = `session-restore-process-allowlist`, matched as whitespace-delimited prefixes so `npm run dev` also covers `npm run dev --port 3000`), `All running processes`. `session-restore-banner` (default `true`) shows "Closed at" / "Restored at" banners. **Crash recovery**: if Otty exits unexpectedly, the next launch offers to restore your open windows from the last known snapshot; snapshots are written whenever a tab is created, closed, or its layout changes, "so at worst you lose seconds of state". Custom agent launch commands: `agent-command = claude=claude --dangerously-skip-permissions` makes the recovery command `claude --dangerously-skip-permissions --resume <id>`. Recipes vs recovery: "Recovery is automatic and short-term. Recipes are intentional, portable, and can include command replay."
**Frequent folders (frecency).** A built-in zoxide-like database — no extra binary, no shell plugin — powering `otty jump`, Open Quickly's Folders filter and folder suggestions in autocomplete. Three feeds: **automatically as you cd** — every working-directory change an Otty pane reports is recorded, which with Shell Integration on is a precise `OSC 7` signal on each prompt, and without it Otty falls back to polling the foreground process's cwd; this is controlled by `frecency-auto-record` (default `on`); **explicitly, with `otty learn`** (`otty learn` records the current directory, `otty learn ~/projects/api` a specific folder — handy for a directory you want later but haven't cd'd into through Otty yet); and **imported from zoxide** (`otty import zoxide` / `otty jump:import`, a one-off merge of zoxide's scores into Otty's database). `otty jump <query>` sends the focused pane to the highest-ranked directory whose path contains the query (case-insensitive substring); ranking order is exact folder-name match, then a name that starts with the query, then a name that merely contains it, then a path-only match, ties broken by frecency score; repeating the same query cycles past the current directory to the next-best match; bare `otty jump` toggles between `$HOME` and your last jump. With **Omit otty prefix** on, `jump` becomes a shell function that resolves the path and `cd`s locally so nothing is echoed into the pane; map it shorter with `cli-alias = j=jump`. Score model: each visit adds 1 to the folder's raw score, scaled at read time by recency — `< 1 hour` ×4, `< 1 day` ×2, `< 1 week` ×0.5, older ×0.25; Otty keeps the **top 100 folders** by decayed score and quietly trims the rest. Curation: the Manage Jump Folders editor (Settings → Shell → Frequent Folders → Manage Folders…) — a Tracked / Ignored segmented control at the top, each row showing the folder and its current Score, with Add… (by hand, before you've ever cd'd into it), Remove, Clear All, Ignore (send a tracked folder to the black-list so it stops showing up) and Unignore — the Open Quickly Folders actions (Open in New Window · Split Right / Down, Change Directory Here, Reveal · Copy Path, Forget This Folder), and the CLI mirrors — `otty jump:add ~/projects/api`, `otty jump:remove ~/tmp/build`, `otty jump:view api`, `otty jump:ls` (top 100; `otty jump:ls 20` for the top 20), `otty jump:import`. `jump:remove` deletes an entry but doesn't stop re-recording; a directory you never want suggested should be black-listed with `otty ignore <path>`, and ignoring is sticky (cd-ing back won't resurrect it). If the external zoxide binary is present, `otty ignore` also runs `zoxide remove <path>` (`zoxide-enabled`, default `on`; `otty learn` is never synced because zoxide's own prompt hook would double-count it). `open-quickly-folders-limit` (default `12`) caps how many folders the picker shows.
**Data sync.** **In Development.** Otty stores configuration, fonts, themes and recipes under `~/.config/otty`, so for now sync/backup of that folder is the mechanism; "Better data sync, and cross-device experience is still under development."
**SSH / remote development.** **In Development** ("Remote development support is still growing"). Plain `ssh` works as in any terminal; on top of that you can use `otty` on the server you connected to. Related shipped surface elsewhere in the docs: the ssh wrapper / terminfo probe (`otty ssh terminfo`, `otty ssh doctor`), forwarded shell integration, the Devices tab badge, and the SSH filter in Open Quickly (hosts parsed from `~/.ssh/config`, ↩ connects in the focused pane, ⌘K connects in a new tab or window).
**CLI usage recipes.** The `otty` CLI ships inside the app; Settings → Shell → Install CLI puts it on `PATH` in one click — it **symlinks `otty` into `/usr/local/bin`** (asking for admin if needed), **installs shell completions for bash, zsh and fish**, and **installs config-file syntax highlighting for Vim/Neovim and bat** (only for the editors you already use). Verify with `otty --version` / `otty <TAB>`. Running `otty` with no subcommand (or starting with `-e`) launches the GUI, so `otty` and `otty -e <cmd>` behave like xterm / alacritty / ghostty; many subcommands that inspect or drive the UI require a running Otty app.
```bash
otty open                              # new window in the current directory
otty open ~/projects/api               # new window rooted at a folder
otty open . --command "npm run dev"    # run something on launch
otty open . --title "API"              # name the window

otty view ./README.md                  # read-only preview, in a new tab
otty edit src/lib.rs                   # editable
otty view https://doc.otty.sh          # http(s) links open as a web pane
otty view user@host:/etc/hosts         # remote paths, over your ssh session
otty view log.txt --new-window
otty edit notes.md --right             # --left / --right / --top / --bottom

otty watch cargo build --release
otty watch -- make test               # `--` before commands with their own flags
otty watch -q ./deploy.sh              # -q: no system notification on finish

otty jump api                          # best frecency match
otty jump                              # toggle $HOME ↔ last jump
otty learn ./scripts/deploy.sh         # project script → folder-scoped suggestion
otty learn "make test-e2e"
otty learn rg                          # probe a $PATH tool's --help ( -y to skip confirm)
otty ignore ~/tmp/scratch              # undo learn for a folder
otty pane send-text --pane "$OTTY_PANE_ID" '\x03'          # a real Ctrl-C
otty pane send-text --pane "$OTTY_PANE_ID" 'git status\n'  # type it and submit
otty pane send-text --pane "$OTTY_PANE_ID" --from-file deploy.sh
otty pane run --pane "$OTTY_PANE_ID" -- npm test && echo "green"
otty pane run --pane "$OTTY_PANE_ID" --format json -- ./deploy.sh
otty pane exec --pane "$OTTY_PANE_ID" --format json -- cargo build
otty pane wait --tab t_19f0bfe5ce9_1a --timeout-secs 300
open otty://pane/$OTTY_PANE_ID
otty open ~/work/team.ottyrecipe
```
Selector forms for the deep links: `otty://window/<sel>` — `w_<id>`, or `current` / `last` / an index / `title:<pattern>`; `otty://tab/<sel>` — `t_<id>` or a 1-based index; `otty://pane/<sel>` — `p_<id>` or a session id (e.g. `$OTTY_PANE_ID`). `otty ignore` semantics: a **folder** leaves the frecency rankings and won't come back when you cd into it (and `zoxide remove` runs too, if zoxide is installed); a **command or script** is forgotten from the current folder's autocomplete — run it from the same directory you learned it in, with the same text, and that half is purely local (no running app needed); a tool's completions learned from `--help` can only be dropped with Settings → Controls → Clear my data.
Driving a pane from a script or agent is off by default (Settings → Advanced → IPC Allow Send Keys) and additionally refused on a pane in an SSH or sudo session unless IPC Allow Sensitive Sessions is enabled; target a pane with `--pane` (omit for the active pane), `$OTTY_PANE_ID`, or the ids from `otty pane list`. `send-text` interprets C-style escapes (`\x03` = a real Ctrl-C) and appends nothing automatically — include a trailing `\n` to run what you sent; `--from-file` / `--stdin` send bytes untouched. `run` submits a command, blocks until it finishes and reports process state (succeed / error) rather than output, exiting with the command's own exit code (JSON form: `{ "state": "succeed", "exit_code": 0, "command": "./deploy.sh", "duration_ms": 1234 }`); it never buffers output, so it is immune to output size, scrollback limits and pagers, and needs shell integration active plus an idle prompt. `exec` is like `run` but separates stdout and stderr (by redirecting stderr before it merges onto the terminal), so `stderr_is_tty` is always false and a program may drop colours or progress bars; it returns `{ "exit_code": …, "stdout": …, "stderr": …, "stderr_is_tty": false }`. `wait` waits for work already running, never types anything, exits 0 as soon as the pane is idle (for an agent pane, idle is what the agent reports; for an ordinary shell pane it needs shell integration), exits **6** if the pane can report neither and **9** on timeout naming the panes still busy. `capture` returns a snapshot of the rendered grid, so pager output comes back as it looks on screen.
Omit the prefix: Settings → Shell → Omit otty prefix installs shell functions for `edit`, `view`, `watch`, `jump` and `learn`; the toggle is live (takes effect at the next prompt in every integrated shell, no restart), wrappers won't clobber an existing name unless `cli-allow-overwrite` (Allow overwrite) is on, and the `jump` wrapper cds the shell locally instead of echoing `cd '<path>'`. Custom aliases (`cli-alias = j=jump`, `v=view`, `e=edit`) apply at shell init — open a new shell after changing them; an alias pointing at a wrapped command goes through that wrapper.

## 6. Configuration surface

Config file `~/.config/otty/config.toml`; per-machine overrides in `~/.config/otty/config.local.toml` (never created by Otty; same format; the Settings panel respects the split and saves a change to whichever file the value comes from, writing a `(reset to default)` line when a local setting is reset; `otty config set --local <key> <value>`, `otty config get <key> --show-origin`, `otty config path --local`, `otty config edit --local`; `otty config unset` without `--local` removes the key from both files). How the two files combine: a key in `config.local.toml` wins over the same key in `config.toml` and every other key still comes from `config.toml`; **a list is replaced, not extended** — if the local file has any `open-with-app` (or `env`, `keybind`, …) lines, those lines are the whole list on this machine and none of the `config.toml` entries are added; and a `# key = … (reset to default)` line keeps that key at its default on this machine whatever `config.toml` says. Settings → Advanced → Reset All Settings empties both. Grammar: flat `key = value`, one assignment per line, `#` comments (a trailing `# …` would become part of an action), quotes around simple strings optional, unknown keys silently ignored so a newer config stays loadable on an older build. Value types: string, integer, float, boolean (`true`/`false`, also `on`/`off`), color (`#RRGGBB`, `#RRGGBBAA`, named), enum, list. Two list spellings — **repeated key** (`keybind`, `env`, `cli-alias`, `hint-pattern`, `agent-command`, `agent-quota-off`, `open-with-app`, `open-with-command`, `profile`, `tab-rule`, `details-view`, `autocomplete-history-ignore`; an entry is the rest of the line so it may contain commas) and **inline array** (`font-family-fallback` and its bold/italic variants, `widen-ambiguous`, `link-scheme-allowlist`, `shell-integration-disabled-shells`, `notification-sound`, `session-restore-process-allowlist`, `progress-bar-commands`; `[]` empties the list). `include = <path>` (repeatable; later includes override earlier ones, the main file is read last and overrides everything). `~` and `$VAR` expand inside string values. Saving hot-reloads every window with no restart or signal; force a re-read with Settings → Advanced → Config File → Reload Config or the Reload Config command. The Settings window and `otty config set` edit the file in place rather than regenerating it, so: comments, blank lines and key order survive (an existing key is updated where it sits, a new one is appended at the end); unrecognised keys are left alone, so a file shared with a newer version keeps its newer keys; a setting you reset is commented out as `# cursor-style = bar (reset to default)` so you can see what it used to be; and **a key written under an alias is rewritten under its real name** (`shell` → `command`, `font-bold` → `text-bold`), value unchanged, so that resetting it later actually clears it. From the CLI, `otty config get <key>` prints one entry per line and `otty config set <key>` takes the whole list back or a **signed entry** to change one (`+EDITOR=nvim` add/replace, `-EDITOR` remove; sign every entry or none — a mixed value is rejected; `config set` prints the resulting list).

**Import / Export** (config converter; full key tables `spec/corpus/import-export.md`). Settings → Advanced → Config File has Import / Export rows with a source picker (Ghostty / Kitty / Alacritty), or CLI `otty import <source> [path]` and `otty export <source> [-o path]`. This is not the Theme importer above (iTerm2 `.itermcolors` etc.) — it converts *settings files*. Every source line lands in one of four buckets: **Supported** (same key, written as-is or value-translated); **Conflict** (same key, different current value — per-row keep vs overwrite); **Similar** (close analog, e.g. `window-padding-x` ≈ theme `[container].padding` — shown as a note, never auto-written); **Source-only** (source has it, Otty does not — listed with a docs link). Export collects every Otty key the target cannot express into a dropped list (stderr in text mode, JSON otherwise); the exported file is a complete drop-in for the target. Default paths: Ghostty `~/.config/ghostty/config` (macOS fallback `~/Library/Application Support/com.mitchellh.ghostty/config`); Kitty `~/.config/kitty/kitty.conf`; Alacritty `~/.config/alacritty/alacritty.toml` (TOML only — older YAML is not parsed). Ghostty is line-based `key = value` like Otty; most appearance/behavior keys map straight through (`font-family`, `theme`, `keybind`, `palette`, …). Kitty uses `key value` (space, no `=`) with `_` in names; the adapter converts `font_family` → `font-family` and value-translates (`cursor_shape beam` → `cursor-style = bar`); `map` and `include` are similar (Otty does not chase includes). Alacritty flattens nested TOML (`font.normal.family` → `font-family`); `[colors.normal]` / `[colors.bright]` → `palette`; `[[keyboard.bindings]]` similar. CLI: a bare `otty import ghostty` previews with no write; `--overwrite` takes the source on every conflict; `--keep` applies only non-conflicting keys; `otty --json import ghostty` is the same report, pipeable. GUI: pick a source, browse off the default path if needed, then a summary dialog with per-row Overwrite/Keep plus bulk buttons; **Apply Import** writes.

## 7. Accessibility, AppleScript, performance

**Accessibility** (requires Otty 1.2.0 or later). Otty is custom-rendered but exposes the parts of the app macOS accessibility clients need: the terminal viewport, selection, cursor position, tab and pane chrome, toolbar buttons and common commands. **VoiceOver**: when running, Otty exposes the visible terminal viewport as text — VoiceOver can read the current screen, move through lines and characters, track the insertion point and read the current selection — and Otty posts cursor and selection updates while VoiceOver is active so typing and navigation at the prompt can be announced without polling every frame. VoiceOver "what to expect": the terminal pane is exposed as text with line and character ranges; native selections are exposed as selected text; the insertion point follows the active terminal cursor; older output is read by scrolling back and then reading the newly visible viewport; and full-screen terminal apps are read as the text they draw — their internal buttons, tables and widgets are not exposed as native macOS controls unless the app also prints meaningful text for them. **Keyboard access**: most actions are reachable from menus, default shortcuts or the Command Palette — Command Palette ⌘⇧P, Open Quickly ⌘⇧O, Find ⌘F, Global Search ⌘⇧F, Settings ⌘,, New Tab ⌘T, New Window ⌘N; every default keybinding is changeable in Settings → Key Bindings. **Accessible chrome**: custom-drawn controls are labelled for assistive technologies — tab rows, close buttons, title-bar controls, pane controls, toolbar buttons, file-panel actions and warning pills — and the terminal stays keyboard-first (Command Palette, Open Quickly, Find, Hint Mode, Vi Mode as alternatives to mouse targeting). **Visual comfort** defaults and useful settings (the snippet below is illustrative, **not** the shipped defaults): blinking text is off by default — programs can still request blink with SGR, but Otty renders it steady unless `text-blink = true`; cursor animation is off by default; font family, font size, line height, cursor shape, cursor blink, selection colors and contrast behaviour are all configurable; `minimum-contrast` can raise foreground/background contrast for low-contrast terminal colors; and smooth scrolling and cursor animation can be disabled if motion is distracting. The snippet the page offers is `text-blink = false`, `cursor-animation = "off"`, `minimum-contrast = 1.0`, `terminal-scroll-smooth = false`, `font-size = 14`, and most of these are also available in Settings → Appearance, Settings → Controls or Settings → Advanced. **Secure input**: with Auto Secure Input enabled Otty turns Secure Keyboard Entry on automatically when the active session appears to be asking for a hidden password (sudo, ssh, login) and releases it when the prompt finishes; it can also be toggled from Edit → Secure Keyboard Entry. **Known limits**: a terminal program controls the text it prints, so Otty can expose the screen faithfully but cannot always infer higher-level semantics such as "this ASCII rectangle is a button" or "this row is selected in the app's internal table". Current limitations listed: VoiceOver reads the visible terminal viewport, not the entire scrollback at once; inline images and graphics are visual content and carry no alt text from terminal protocols; per-cell color and style information is not exposed as spoken semantic annotations; and some custom-drawn panels may expose labels and actions without the same structure as fully native AppKit controls.
**AppleScript automation** (requires Otty 1.2.0 or later; ships in the app, nothing to install). The dictionary is drop-in compatible with Terminal.app's most common verbs — most scripts work by changing the application name to "Otty". Core verb `do script`: with no target it opens a new window and runs the command there; `do script "git status" in front window` (the window's selected tab) and `do script "npm test" in tab 2 of window 1` target existing containers; `do script` **returns the tab it ran in**, so `set buildTab to do script "make release"` then `set custom title of buildTab to "Release Build"` works. Tab properties: `contents` (text currently visible on screen), `history` (full scrollback plus visible screen), `busy` (`true` while a foreground process that isn't the shell is running), `processes` (names of processes in the tab), `tty` (the device path, e.g. `/dev/ttys003`), `number of rows` / `number of columns`, `working directory`, `id` (the session id, also a selector for the `otty` CLI). Common patterns: read `contents of t` after a delay; loop `repeat while busy of t` / `delay 0.2` then read `history of t`. Also: `set custom title of selected tab of front window to "Deploy"` (pins the title against shell updates), `set custom title of … to ""` (restores the shell-provided title), `set selected of tab 3 of window 1 to true`, `count windows`, `get name of front window`. **Security** (AppleScript): `do script` is allowed by default so automation just works, but SSH sessions and privileged (sudo) sessions are protected — `do script` into them is refused and `contents` / `history` return empty (the page says "two guards apply" but bullet-lists one; the second is the config override). This mirrors the CLI's `pane send-keys` / `pane capture` protection; to let automation reach remote or privileged panes intentionally, set `ipc-allow-sensitive-sessions = true`. For shell scripting, `otty open`, `otty tab new`, `otty pane send-keys` and `otty pane capture` cover the same ground cross-platform, with `$OTTY_PANE_ID` to target the caller's own pane.
**Performance.** Render pipeline: **macOS — native Metal renderer, one GPU layer per pane**; **Windows (planned) — native DirectX 12 renderer** (`[conflict]` the Unicode and Text Styles page states plain "Metal on macOS, DirectX 12 on Windows", without marking the Windows path as planned); subpixel-aware glyph caching, so a repeated glyph is rendered once and reused; and inactive tabs can release their renderer resources entirely (`freeze-inactive-tab`). Memory: **sparse-row grid storage** — only cells that have ever been written are allocated, so empty scrollback rows are free; scrollback capped per pane at `scrollback-rows = 10000        # default` (the Performance page's spelling — the Configuration Reference's equivalent key is `scrollback-lines = 10000`, **[conflict]**); and inline images use a small atlas with eviction, with very large or rare images bypassing it. Benchmarks via vtebench — "each test streams a fixed ~1 MiB of escape sequences and records how long the terminal takes to parse and render it. Lower is faster"; the page explicitly frames these as "a sample benchmark to show Otty is fast enough — not a claim that Otty is definitively faster than Ghostty", a rough sanity check rather than a leaderboard.
